## Находки

### Н-1 (средняя). Сторно тестового расхода в live записывается боевым

- Где: `bl.set_is_test` (`supabase/migrations/1001_clubs_is_test.sql:38–71`) для `cashbook_entries` берёт `is_test` по режиму клуба, а не по исходной записи (подтверждено оркестратором чтением).
- Шаги: клуб в `test` → расход (событие обслуживания со стоимостью или ручной) `is_test = true` → `go-live` → исправление события (`server/maintenance/service.mjs:346–354` → `stornoEntry`, `server/dashboard/cashbook.mjs:257`) или `POST …/cashbook/{id}/storno` → сторно −X с `is_test = false`.
- Итог: боевые расходы уменьшаются на X, прибыль растёт без денег, владельцу ничего не приходит. Путь через кассу — с M5.2, M5.6 добавил путь через обслуживание.
- Предложение: сторно наследует `is_test` исходной записи; проверить все таблицы с обратными записями. Владелец — backend.

### Н-2 (низкая). Поток уведомлений `maintenance.due`

- Ключ отметки `(стол, вид, событие, порог)` (`1250_maintenance.sql`, `maintenance_alerts_once`): управляющий меняет порог (`PUT …/maintenance/thresholds`, 30/мин) → на следующем проходе (раз в 10 минут) новое уведомление владельцу по каждому столу. Общего лимита нет, смена порогов и выключение `null` владельцу не сообщаются.
- Предложение: лимит уведомлений на клуб в сутки, уведомление владельцу о смене порогов. Владелец — backend.

### Н-3 (низкая). Исправление комментария вносит расход заново

- Если расход события уже сторнирован вручную, исправление только комментария берёт стоимость из исходного события (`service.mjs:318`) и вносит расход снова (`:356–367`); интерфейс шлёт только изменённые поля (`web/admin/src/lib/maintenance.js:180–190`) и не предупреждает.
- Предложение: новый расход — только при явном `cost_kopecks`. Владелец — backend, frontend.

## Выдержало (по коду)

- Только дополнение: триггеры `enable always` на UPDATE, DELETE, TRUNCATE; RLS ENABLE и FORCE; у `app_api` только select и insert.
- Чужой клуб: составные FK `(club_id, …)` для стола, `corrects_id`, `event_id`, `maintenance_event_id`; поиск с `club_id` → 404.
- Двойное исправление: уникальный индекс по `corrects_id` → 409, одна транзакция. Повтор с тем же `Idempotency-Key` — сохранённый ответ; с другим телом — 409.
- Деньги: целые копейки до 10⁹ ₽; даты 366/35 суток; задним числом — уведомление владельцу (№189).
- Права: ресепшн и бар — 403; кэш прогноза и дашборда после проверки прав, `club_id` в ключе.
- Вход: `date`, `kind` строго, SQL параметризован; мусор в `maintenance_thresholds` → значения по умолчанию.
- Прогноз: клуб в `test` — нет прогноза; сутки до `went_live_at` не входят; «все клубы» — только свои.
- ПДн: комментарии и причины маскируются, в уведомлении их нет. Журнал: `maintenance.*` через `appendAudit` в цепочке.
- Экран ключей и вебхуков: ключ и секрет только в состоянии окна, очищаются при закрытии; не в localStorage, URL, консоли; вывод текстом, `innerHTML` нет.
