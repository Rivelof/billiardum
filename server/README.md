# Сервер «Бильярдума» (`@billiardum/server`)

Вход `index.mjs`: HTTP на `PORT` (`GET /health` и API `api/routes/*.mjs`), модули core → light → money. Контракты — `docs/contracts/m0.md` §6 и `docs/contracts/m1.md` §2–4, §7, §13; протокол — `docs/protocol.md`.

## Команды

| Команда | Что делает |
|---|---|
| `node server/index.mjs` | сервер; по `SIGTERM`/`SIGINT` перестаёт принимать соединения, закрывает потоки SSE, останавливает money → light (или мост M0) → outbox, закрывает пул базы |
| `npm test -w @billiardum/server` | юнит-тесты без базы и брокера: протокол, мост, роутер, вход, initData, PIN, Web Push (вектор RFC 8291), PDF и QR, SSE, прокси; плюс `tariffs/test`, `payments/test` (money) |
| `npm run test:db -w @billiardum/server` | тесты core на временной базе (`DATABASE_ADMIN_URL`, как `npm run test:db`): вход, CSRF, PIN, идемпотентность, outbox, журнал, тревоги, уведомления, маршруты владельца, SSE |
| `npm run provision:dev` | только разработка, ниже |
| `node server/bin/telegram-webhook.mjs [--delete]` | `setWebhook` бота на `https://{PUBLIC_HOST}/api/bots/telegram/webhook` с `secret_token` через прокси |

## Сборка (`index.mjs`, `http/app.mjs`)

Общий контекст `ctx` (контракт §2.1): `{ config, log, pool, clock, outbox, alarms, notify, sse, audit, telegram, bridge, withContext, modules }`. `withContext` — функция M0 `withContext(pool, { clubId, userId, actorType }, fn)`. Модули поднимаются по порядку через `init(ctx)` и останавливаются `stop()` в обратном порядке (`http/app.mjs`, `MODULES`): `sessions` (light) → `payments` (money) → `catalog` → `stock` → `orders` (pos) → `kkt` → `packages` → `bookings` → `waitlist` → `summaries` (модули M3 соседей подключаются, когда появятся файлы). WebSocket моста ККТ: событие `upgrade` HTTP-сервера отдаётся `kkt.handleUpgrade` (`/api/kkt/ws`), остальные upgrade закрываются. Остановка (`app.shutdown`): `server.close()`, затем сразу закрываются потоки SSE и мосты ККТ (`kkt.closeConnections`), иначе `close()` ждал бы их; затем модули и outbox. Нет файла модуля — лог `module_missing`, сервер работает без него; пока нет light, мост MQTT создаётся как в M0 (`bridge_fallback_m0`). Ошибка внутри модуля — сервер не стартует.

## HTTP API (`api/router.mjs`)

Подключает все `api/routes/*.mjs` (`export const routes = [...]` или `routes(config)`). Маршрут: `{ method, path, auth, roles?, handler, requires?, idempotent?, rateLimit?, actor?, clubFromBody?, findClub?, enabled? }`.

- Роли в клубе: `owner`, `manager`, `reception`, `installer`, `bar` (бармен, №97: экран бара, статусы заказов, стоп-лист; права задают маршруты модулей; по PIN на терминале входят `owner`, `manager`, `reception`, `bar`).
- `auth`: `none` — без входа; `guest` — любой вошедший пользователь; `staff` — роль из `roles` в клубе запроса; `terminal` — токен терминала ресепшена; `any` — пользователь или терминал.
- Вход: `Authorization: Bearer <token>` или cookie `bl_session` (`HttpOnly; Secure; SameSite=Lax; Path=/api`). Токен — 32 байта base64url, в базе только sha256, проверка — `bl.auth_resolve`.
- Клуб запроса: `{club}` в пути → `body.club_id` (`clubFromBody`) → `?club=` → заголовок `X-Club-Id` → клуб токена PIN или терминала → единственный клуб пользователя с ролью из `roles` (несколько — `findClub` ищет объект в каждом, иначе `400`). У `auth: 'none'` клуб только из пути или `ctx.useClub(id)` в обработчике.
- Транзакция `withContext` на запрос: `actor_type = user` и `app.user_id`; вебхуки с `actor: 'system'` работают в контексте платформы. Обработчик: `async handler(ctx, req) → { status, json } | { status, headers, body } | { status, stream(res) }`; `ctx = { ...общий контекст, db, user, club, clubMode, roles, principal, idempotencyKey, useClub(id), setCookie(header), afterCommit(fn), manual(entry) }` (M5.1: `clubMode` — режим клуба запроса `test` | `live` | `suspended`, в транзакции — `app.club_mode`; `manual` — ручное действие: причина, журнал `manual.*`, тревога владельцу, `lib/manual.mjs`). `afterCommit` — после коммита (SSE, MQTT); при откате не выполняется.
- Ошибка: брошенный `HttpError` (или любая ошибка с `status` и `code`) — откат и `{"error":"code"}`; прочие — `500 {"error":"internal"}`, подробности только в лог. Словарь — `http/errors.mjs` (контракт §3, плюс `no_tariff`, `not_configured`, `method_not_allowed`, `internal`).
- Изменяющие запросы: `Content-Type: application/json` обязателен (`415`), тело — объект JSON до 64 КБ (`413`, `400`). Запрос с cookie — только с `Origin` из `https://{PUBLIC_HOST}` (и `https://{DEV_LAN_HOST}{порт}` не в проде, `ALLOWED_ORIGINS`); чужой `Origin` — `403` всегда, с Bearer тоже.
- `rawBody: { types, maxBytes }` (M5.1 №157) — тело с таким `Content-Type` (например `.xlsx`, `multipart/form-data`) читается как есть до `maxBytes` в `req.rawBody = { mime, contentType, buffer }`, `req.body = {}`; JSON такой маршрут принимает как обычно.
- `requires: ['phone', 'consent']` — `403 phone_required` / `403 consent_required`.
- `idempotent: true` — `Idempotency-Key` (UUID) обязателен; повтор с тем же ключом (пользователь, ключ, маршрут) 24 часа — тот же ответ с `Idempotent-Replayed: true` без исполнения; тот же ключ с другим телом — `409 idempotency_conflict`; параллельный повтор ждёт коммита первого. Ошибка, брошенная обработчиком, не сохраняется.
- Ограничение частоты — в памяти, на IP и маршрут (по умолчанию 600 в минуту, `rateLimit` маршрута), `429 rate_limited` с `Retry-After`. IP: адрес сокета; `X-Forwarded-For` (последний адрес) — только если соединение пришло из `TRUSTED_PROXY_CIDRS` (в разработке по умолчанию loopback и частные сети — Caddy в сети Compose). В `NODE_ENV=production` (M4-I4) `TRUSTED_PROXY_CIDRS` обязательна (без неё сервер не стартует), а она и `PUBLIC_API_TRUSTED_CIDRS` — только сети не шире /24 (IPv4) и /120 (IPv6), иначе `config_error`.
- Заголовки ответов: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Cross-Origin-Resource-Policy: same-origin`. Внешних ресурсов сервер не отдаёт и не подключает.

## Вход (`auth/`, `api/routes/auth.mjs`, контракт §4)

| Маршрут | Суть |
|---|---|
| `POST /api/auth/dev {phone}` | только `NODE_ENV ≠ production` и `ALLOW_DEV_LOGIN=1`; иначе маршрут не регистрируется |
| `POST /api/auth/telegram {init_data}` | HMAC-SHA256: секрет = HMAC(«WebAppData», токен), `hash` за постоянное время, `auth_date` ≤ 24 ч (и не из будущего > 5 мин); `{token, user, needs_phone}` |
| `POST /api/auth/max` | `501 not_configured` до документации MAX |
| `GET /api/auth/methods` | без входа: `{methods}` — только реально работающие способы входа из `telegram` (бот: токен, имя, секрет вебхука и прокси), `max` (пока нет — заглушка), `dev` (не production и `ALLOW_DEV_LOGIN=1`); кнопки недоступных способов не показывать (U1) |
| `POST /api/auth/bot-link {channel}` | nonce 32 байта (в базе sha256, 10 минут), `deep_link = https://t.me/<бот>?start=<nonce>`, `code` — 6 цифр для показа на экране, cookie `bl_link` с секретом браузера; `max` — 501. Бот после Start просит ввести код с экрана; `done` — только после верного кода (3 неверных — `expired`), затем контакт, если телефона нет (ревью входа п. 2, миграция 0704). После выдачи токена — сообщение в бот «вход на новом устройстве» с кнопкой «Выйти везде» (callback `logout_all` отзывает все токены пользователя) |
| `GET /api/auth/bot-link/{nonce}` | `pending` / `expired` / `done` + токен — один раз и только браузеру с `bl_link` |
| `POST /api/bots/telegram/webhook` | `X-Telegram-Bot-Api-Secret-Token` = `TELEGRAM_WEBHOOK_SECRET`; `/start <nonce>` → кнопка «Поделиться контактом» (телефон уже известен — сразу вход); свой контакт → телефон (`bl.auth_attach_phone`), nonce → done; ответы бота — после коммита, через прокси |
| `POST /api/auth/consent {version}` | версия = `CONSENT_VERSION` (по умолчанию `2026-10-21`) |
| `POST /api/auth/logout`, `GET /api/me` | выход (токен отзывается, cookie стирается); `{user, clubs, session}`: `user` — `name`, `phone_masked`, `needs_phone`, `consent_version` (`null` без согласия), `consent: {version, accepted}`, `notify_channel`; `clubs[]` — `club_id`, `role`, `name`, `timezone` |
| `PATCH /api/me {name?, notify_channel?}` | своё имя (1–100 символов, для персонала: журнал, терминал) и основной канал уведомлений |
| `POST /api/staff/terminal {club_id, name}` | владелец, управляющий (личный вход): `{terminal_token, terminal_id}`, журнал `auth.terminal_register` |
| `GET /api/staff/terminal` | терминал: персонал клуба `[{user_id, name, role, phone_masked, pin_set}]` (выбор сотрудника перед PIN) |
| `POST /api/staff/pin {user_id, pin}` | терминал: токен PIN на 12 ч только в клубе терминала, предыдущий сотрудник терминала выходит; журнал `auth.pin_switch {terminal_id}`; 5 ошибок подряд — блок 15 минут (`429`) |
| `checkStaffPin({pool, clubId, userId, pin, roles, pepper, now?})` (`server/auth`) | проверка PIN сотрудника без смены пользователя терминала (одобрение скидки управляющим, №95): своя транзакция, счётчик ошибок коммитится при любом исходе вызывающего; блок 5 ошибок / 15 минут общий со сменой по PIN; `{ok: true, role}` или `{ok: false, code: bad_request\|unauthorized\|forbidden\|rate_limited, retryAfterSec?, locked?}` |
| `PUT /api/staff/pin {club_id, pin}` | сотрудник сам задаёт PIN (4–6 цифр, scrypt N=16384 с солью и «перцем» из `SECRETS_ENC_KEY`), журнал `auth.pin_set` |

Вход персонала через бота или `dev` пишет `auth.staff_login` в журнал каждого клуба, где он сотрудник. Телефон из контакта уже есть у другой учётки (сотрудник из сида, вход через другой мессенджер) — учётка мессенджера вливается в неё (`merged_into`), её токены перестают действовать; у той учётки другой Telegram — `phone_conflict`, бот сообщает. Telegram — только через `TELEGRAM_PROXY_URL` (`http://` — CONNECT, `socks5://`), `lib/http-client.mjs`; без токена или прокси канал выключен.

## Outbox (`outbox.mjs`, контракт §2.2)

`enqueue(db, topic, payload[, { clubId }])` — в транзакции вызывающего (клуб — из контекста). `subscribe(topic, handler, { name })` — обработчик в своей транзакции с контекстом клуба события, вместе с отметкой `bl.outbox_done`; ошибка — повтор через 1, 2, 4 … 300 с, после 5 неудач — тревога `outbox_failed` (critical) клубу. Доставка «хотя бы один раз»; сбой одного подписчика не держит остальных. Задержка — `LISTEN bl_outbox` (NOTIFY триггера вставки) и опрос раз в 1 с; у каждой темы своя очередь (№130): медленный обработчик одной темы не задерживает другие, порядок — только внутри темы; обработанные события старше 7 дней удаляются. В `last_error` и логе — только код ошибки, длинные номера маскируются.

## Тревоги и уведомления (`alarms/`, `notify/`, контракт §7)

- `raise(db, clubId, {type, level?, resourceId?, data, manual?, text?})` — в контексте клуба: `bl.alarms`, журнал `alarm.raised`, уведомление владельцам и управляющим, после коммита SSE `alarm` в `club:{id}`. Уровень по умолчанию — `ALARM_LEVELS` (PRODUCT §8, decisions №66). Повтор открытой тревоги того же типа по тому же столу — только `count` (без журнала и уведомлений), **кроме критичной тревоги, о которой не уведомляли ≥ 10 минут** (`last_notified_at`, миграция 0106, decisions №75), и **ручных действий** (`manual: true`, по умолчанию `service_light` и `manual_action`): они уведомляют при каждом вызове (№66), `text` — свой текст уведомления. Ключ склейки — тип + стол + объект: `dedupeKey` или по умолчанию поле `data` (`DEDUPE_FIELDS`: чеки — `receipt_id`, `payment_mismatch` — `payment_id`, `refund_mismatch` — `refund_id`, бар — `sale_id`, расхождение кассы — `shift_id` …; миграция 0108), так что тревоги по разным чекам не глушат друг друга. Возвращает `{id, created, count, notified}`. `ack` — `alarm.ack`.
- `send(db, userId, {kind, text, data, level})`, `sendToClubStaff(db, clubId, roles, msg)` — строка `bl.notifications` (`queued`) и событие outbox `notify.deliver`, обработчик которого только будит воркер. Воркер доставки (№130, миграция 0705) — вне транзакций outbox: захват `sending` + `claimed_at`, 4 уведомления параллельно, общий бюджет 60 с на уведомление (мессенджер — до 30 с), подписки Web Push — параллельно; каждая попытка пишется в `attempts` до вызова канала (`started`) и после: после сбоя процесса захват старше 90 с продолжается с непройденных каналов, в канал с начатой попыткой второй раз не шлём (`unknown`). Цепочка: выбранный порядок (`channels_order`) или основной канал, затем max → telegram → webpush; `important` и `critical` после выбранных каналов уходят и в остальные доступные, `critical` — во все. MAX — `skipped` до документации; Telegram без токена или прокси — `skipped`; лог `notify_skipped`. В тексте и `data` последовательности из 10+ цифр заменяются на `***` (decisions №53); в `data` — числа, короткие строки и массивы из них (до 20), вложенные объекты отбрасываются.
- Web Push (`notify/webpush.mjs`): RFC 8291 `aes128gcm` и VAPID RFC 8292 ES256 на `node:crypto`; тело — `{title, body, url, tag}` (§14). Подписки только на `https` известных push-сервисов (FCM, Mozilla, Apple, WNS; `WEBPUSH_ALLOWED_HOSTS`), 404/410 — подписка отзывается.
- SSE (`http/sse.mjs`): `publish(channel, event, data)`, каналы `club:{id}`, `session:{id}`, `user:{id}`; `GET /api/stream?club=` — ресепшн и выше; бармену — только события `bar`, `stop_list` этого канала (№97); `?session=` — участник или персонал клуба сессии; свой `user:{id}` всегда; keep-alive 25 с, раз в минуту проверка токена и роли, до 10 потоков на пользователя. Мини-приложениям (§14): `POST /api/stream/token {club}|{session}` → `{token, expires_at}` — одноразовый токен на 60 с, привязан к пользователю, его токену входа и каналу (в памяти, только sha256); `GET /api/stream?…&token=` без cookie и Bearer; другой канал, повтор, истёкший — 401.

## M3: цепочка уведомлений, утренняя сводка, персонал

- **Цепочка (№110).** `send(db, userId, {kind, text, data, level?, actions?})` → `{notification_id}`. Каналы — `users.channels_order` (`PATCH /api/me {notify_channel, channels_order}`; только выбранные и доступные), без него — основной канал, затем max → telegram → webpush. Ошибка канала или нет подтверждения мессенджера за 30 с — следующий канал; попытки (`channel:status:code`) и итог — в `notifications`; `critical` — во все каналы. Telegram — только через `TELEGRAM_PROXY_URL`; MAX — адаптер той же формы (`notify/max.mjs`), до документации `not_configured` → сразу следующий канал. Действия `[{id, title, url}]` (до 5, `url` — путь своего сайта): Telegram — кнопки-ссылки, Web Push — `actions` и `url`, MAX — кнопки-ссылки. Проверено на заглушках Telegram и MAX.
- **Утренняя сводка (`server/summaries`, №110, №43, №13).** Модуль `summaries` (планировщик раз в минуту на `ctx.clock`): клубам, у которых по местному времени наступило `settings.summary_time_local` (10:00), — сводка за вчерашние рабочие сутки (с `day_start_local`): выручка по способам и возвраты (`server/reports/queries.mjs`), часы игры и загрузка, тревоги по уровням, ручные действия (`manual.*`; действия системы — `manual_actions.automatic {count, by_action}` и строка «автоматических действий системы: M» при M > 0, №125), полный хеш головы журнала. Владельцу и управляющему (`summary.morning`), один раз — `bl.club_summaries`.
- **Персонал (`server/staff`, `api/routes/staff.mjs`, №111, только владелец).** `GET /api/clubs/{club}/staff` → `{staff, invites}`; `POST …/staff {phone, role}` — приглашение на 7 дней (роли `manager`, `reception`, `installer`, `bar`; уже сотрудник — `409 duplicate`; повтор продлевает); при входе с этим номером приглашение привязывается (`bl.staff_accept_invites`); `PATCH …/staff/{user_id} {role}`; `DELETE …/staff/{user_id}` — членство, PIN и все токены сотрудника (личные и PIN на терминалах) гаснут сразу (`bl.staff_revoke`); `DELETE …/staff/invites/{id}`. Владельца и себя — нельзя (403). Журнал: `staff.invite`, `staff.invite_accepted`, `staff.invite_revoked`, `staff.role`, `staff.revoke`.

- **M4 core.** Роли платформы (№134, миграция 0710): `bl.platform_members` (`platform_operator`, `platform_admin` — Андрей), назначаются миграцией или администратором базы; сид разработки: +70000000009 — platform_admin, +70000000010 — оператор. Маршрут `auth: 'platform'` с `roles` (`ROLES.PLATFORM_OPERATOR` — оператор и администратор, `ROLES.PLATFORM_ADMIN`): только личный вход, без клуба; `ctx.platformRole`, в транзакции `app.platform_role` и `actor_type support` — политики модулей опираются на `bl.ctx_platform_role()` (роль подтверждается базой), `appendAudit` без клуба пишет в журнал платформы от имени сотрудника. `GET /api/me` → `user.platform_role` (`platform_operator` | `platform_admin` | null). Уведомления платформе: `sendPlatform(db, { role: 'platform_operator' | 'platform_admin', kind, text, data, actions, level })` (`ctx.notify.sendPlatform`) — всем операторам (нет активных — администраторам) или Андрею, из любого контекста. Публичные маршруты: опция `cache: N` (GET без входа) — общий ответ 200, `Cache-Control: public, max-age=N` и кэш процесса на N секунд, токен не читается; `/api/public/*` — только GET без входа, по умолчанию `cache: 60` и 120 запросов в минуту с IP; сервис сайта с адресов `PUBLIC_API_TRUSTED_CIDRS` — без лимита. Публичный поток турнира: `GET /api/public/stream?tournament={id}` без входа, только для опубликованного турнира (не черновик, иначе 404, M4-7), канал `tournament:{id}`, только события `bracket`, `tournament`, `match` (публикация других — ошибка), не больше 10 потоков с источника (IPv4 — адрес, IPv6 — сеть /64); анонимные потоки (публичный и ТВ) — не больше четверти хаба (`MAX_ANON_CLIENTS` = 500 из 2 000), остальное — вошедшим; с одной сети IPv6 /56 — не больше `MAX_ANON_PER_NET` = 50 анонимных потоков (M4-I6, `netOf`; так же в запасном ТВ-хабе турниров), иначе одна выдача абоненту заняла бы всю долю и ТВ-экраны других клубов остались бы без обновлений. Следующий шаг (M4-I6): токена ТВ-экрана в модели нет — ТВ-экран клуба сейчас в анонимной доле; выдать экрану клуба токен (как терминалу персонала) и пускать его поток вне анонимной доли. Маска телефонов (`maskPhones`, M4-5, M4-8): текст сначала нормализуется (`normalizeText`: без невидимых `\p{Cf}`, кроме ZWJ эмодзи; знаки-цифры — полноширинные, надстрочные, «①» — в ASCII по NFKC; остальной текст NFKC не трогает, чтобы «№» и «…» не стали «No» и «...»), разделитель между цифрами — 1–3 любых знака, кроме букв и цифр (в том числе `· , : ~ ...`), с пробелом по краям; 10 и больше цифр — `***`. Не маскируются даты (`21.10.2026`, `2026-10-21`) и списки времени или дат без года (`22:00, 21:30, 23:30`, `25.10, 10.00-22.00`); списки цен через запятую с 10+ цифрами маскируются — допустимое ложное срабатывание. `MODULES`: `directory`, `plus`, `tournaments` подхватываются, если файлы есть. В белом списке полей ошибок — `limit`, `rating` (409 `rating_above_limit`) и `reason` только из закрытого списка кодов `SAFE_REASONS` (`tournament`, `booking`, `service`, `pending`, `offline`, `busy`, `reserved`, `waitlist`, `session`, `maintenance`, `closed`), например 409 `table_busy {reason: 'tournament', busy_until}`; `status` — только из `SAFE_STATUSES` (`accepted`, `declined`, `operator`, `closed`): 409 `request_closed {status}` по ссылке клуба на заявку (T25).
- **Проглоченная ошибка запроса.** `withContext` (`server/lib/store.mjs`) отслеживает ошибки запросов клиента: если обработчик (маршрут, outbox, планировщик) поймал ошибку без точки сохранения и вернул успех, транзакция испорчена — вместо тихого ROLLBACK под видом COMMIT бросается `TxAbortedError` (`code: 'tx_aborted_swallowed'`, `swallowedAt` — стек запроса): у роутера 500 `internal` и лог `tx_aborted_swallowed`, у outbox — повтор. Ловить ошибки соседей — через `safely(db, fn)` (точка сохранения: откатывается только fn, транзакция остаётся рабочей). Утренняя сводка: `revenue.tournaments.total_kopecks` и строка «турниры N ₽» при N > 0.
- **Одно соединение пула на обработчик (pentester R-1).** Обработчик с транзакцией запроса (`ctx.db`) не открывает вторую транзакцию `withContext(ctx.pool, …)` и не ждёт её: при параллельных запросах числом с пул это взаимная блокировка пула. Если нужны отдельные коммиты (счётчик ошибок PIN), маршрут объявляется `db: false` (для `auth: 'none'` и `'terminal'`): без транзакции запроса, короткие транзакции по очереди, `ctx.setCookie` есть, `afterCommit` нет; так сделан `POST /api/staff/pin`. Outbox обрабатывает одновременно не больше `LANES` (4) событий разных тем.
- **Данные в ошибках и пояс клуба.** Ошибка с `status`/`code` может нести `data`: наружу рядом с `error` уходят только поля `SAFE_ERROR_FIELDS` (`booking_id`, `session_id`, `resource_id`, `offer_id`, `payment_id`, `busy_until`, `limit_until`, `extend_limit_until`, `available_from`, `retry_after_sec`, `minutes_left`) со значениями UUID, время ISO, целое, логическое или null; у 5xx — без данных (`server/http/errors.mjs`, `safeErrorData`). Пример: 409 `{error: 'booking_start_required', booking_id}`. Пояс клуба при записи — `isValidTimeZone` (`server/lib/timezone.mjs`: `Intl.supportedValuesOf('timeZone')` и UTC); в базе `bl.is_valid_timezone` (0707) — UTC или IANA Область/Место, без сокращений и posix/….
- **Ревью M3 (№130, ревью входа).** `PATCH /api/me` принимает только каналы из `channels_available`. Отзыв сотрудника (`bl.staff_revoke`, 0706): PIN-токены клуба и терминалы клуба, заведённые им; личные токены — только если других активных членств нет. Терминалы (владелец): `GET /api/clubs/{club}/terminals` → `[{id, name, created_by: {user_id, name}, created_at, expires_at, last_used_at, revoked_at, locked_at}]`, `DELETE …/terminals/{id}` — отзыв (PIN-токены на нём гаснут), `POST …/terminals/{id}/unlock`. 10 неверных PIN на терминале за час — вход по PIN на нём закрыт (429) до разблокировки, тревога `terminal_locked` (critical). PIN владельца и управляющего — 6 цифр; вход по старому короткому — `pin_change_required: true` в ответе `POST /api/staff/pin`. Поток SSE раз в минуту перепроверяет токен через `bl.auth_resolve` (отзыв терминала у токена PIN) и роль персонала в клубе канала `session:`. Сводка ждёт конца рабочих суток, если `summary_time_local` раньше `day_start_local`; неактивные клубы — без сводки.
- **Для frontend (№120).** `GET /api/clubs` без входа → `[{id, name, city, address, timezone, plan: {width_cm, height_cm} | null}]` только активных клубов (`bl.public_clubs()`, миграция 0703: `clubs.address`, `clubs.active`), `Cache-Control: public, max-age=60`, 120 запросов в минуту с IP. `GET /api/stream?me=1` — только свой канал `user:{id}` (события гостя без сессии: лист ожидания, брони; модули публикуют в `user:{id}`), одноразовый токен — `POST /api/stream/token {me: true}`. В `GET /api/me` — `user.channels: {max, telegram, webpush}` (мессенджер привязан; у Web Push — есть действующая подписка). №126: `channels.max`/`channels.telegram` — true, только если мессенджер привязан и его адаптер настроен на сервере (MAX пока заглушка → false; Telegram — нужны токен и прокси); `user.channels_available` — каналы, настроенные на сервере (из `max`, `telegram`, `webpush`; Web Push — при заданном VAPID), только их предлагать в выборе основного канала и порядка. Сохранённые `notify_channel`/`channels_order` отдаются как есть, ненастроенные каналы при доставке пропускаются.

## Мост MQTT (`mqtt.mjs`, protocol v1 §2, §6)

M1: мост создаёт модуль light (`sessions/index.mjs`) — очередь команд `bl.device_commands`, актуальное состояние стола, события в журнал один раз, сверка `state` и тревоги; подробно — `sessions/README.md`. Ниже — поведение M0, которое сохраняется.

- Подключение `bl-server` по TLS с CA из файла, `clean session`, подписка `bl/v1/+/+/{state,status,event,ack}` (QoS 1). Входящие сообщения больше 4096 байт отбрасываются с записью в лог (`message_too_large`).
- Клуб устройства — по `device_id` из базы (`bl.device_club`), а не из топика. Расхождение — лог `device_club_mismatch` (тревога) и запись `device.topic_mismatch` в журнал клуба; сообщения такого топика не обрабатываются.
- Онлайн: `status = online` и получен `state` (после `offline` нужен свежий `state`). Офлайн: `status = offline` или нет `state` больше 150 с.
- Одна неподтверждённая команда на устройство, остальные ждут в очереди. Команда: в одной транзакции под `app_api` с контекстом клуба — `SELECT … FOR UPDATE`, `seq`, расшифровка `device_key`, подпись, запись `device.cmd` (`data = {cmd_id, seq, type}`). Публикация после коммита. Без `ack` 3 с — повтор той же команды байт в байт, до 5 раз, затем `cmd_no_ack` (уровень `error`, тревога «контроллер не отвечает») и отказ от команды; следующая из очереди уходит. Повтор журнал не пишет. Устройство без ключа — `cmd_skipped`, ни `seq`, ни журнала.
- Пока устройство офлайн, повторов и `cmd_no_ack` нет: неподтверждённая команда бросается (`cmd_abandoned`), очередь чистится (`cmd_dropped`); досылается только `config.set` тем же `id` и `seq`. Команды офлайн-устройству не ставятся (`command()` → `offline`).
- После выхода онлайн и после события `boot` — актуальное состояние стола (`actualState`). В M0 это `ping`: сессий нет, симулятор M0 исполняет только `ping` и `identify`. В M1 сюда встаёт `session.resume`, `service.start`, `state.pending`/`state.reserved` или `state.free`. `boot` в течение 10 с после выхода онлайн — та же загрузка, второй раз состояние не шлётся.
- Сверка: `seq = greatest(devices.last_seq, state.last_seq) + 1`. Подъём по `state` — запись `device.seq_sync` (`{from, to}`) и лог `device_seq_sync`. Разрыв больше 1 000 000 — лог `device_seq_gap` (уровень `error`, тревога) без подъёма.
- `ack` сопоставляется по `cmd_id` и устройству. `ack` с `cmd_id: null` (команда не разобрана, `bad_format`) относится к неподтверждённой команде: её не повторяют.

Логи — строки JSON в stdout без персональных данных:

```
{"t":"…","level":"info","msg":"devices_online","online":8,"total":8}      при изменении и раз в 60 с
{"t":"…","level":"info","msg":"cmd_ack","device_id":"…","type":"ping","seq":1,"ok":true}
```

Также: `device_online`, `device_offline` (`reason`: `status` или `no_state`), `device_event` (только `type`, `boot`, `boot_id`, `n`), `device_unknown`, `cmd_no_ack`, `cmd_abandoned`, `cmd_skipped`, `device_seq_sync`, `device_seq_gap`, `message_too_large`, `mqtt_connected`, `mqtt_disconnected`, `db_error`. При `ok:false` строка `cmd_ack` идёт с уровнем `warn` и полем `error` (код из `ack`).

## Модули `lib/`

- `protocol.mjs` — строгий и канонический JSON, подпись HMAC-SHA256, проверка команды (`bad_format` → `bad_sig`), сборка команды, топики; проходит все 38 векторов. `bad_format`: команда длиннее 2048 байт, обратная косая черта где угодно, повторяющиеся ключи, числа не по исходному тексту (`context.source` в reviver `JSON.parse`: `1.0`, `9e5`, `-0`, ведущие нули, вне ±(2^53−1)), поля не по §3 (`id` — UUID в нижнем регистре, `seq` ≥ 1, `issued_at` — целое ≥ 0, `body` — объект). `bad_sig`: `sig` не ровно 44 символа канонического base64 или не совпадает.
- `secrets.mjs` — AES-256-GCM (decisions №23): `v1:` + base64(iv 12 ‖ tag 16 ‖ шифртекст), AAD `bl.secret/device_key/<device_id>` — ключ одного устройства, переложенный в строку другого, не расшифруется.
- `store.mjs` — транзакции с контекстом клуба (`withContext`), выделение `seq` и журнал.
- `dynsec.mjs` — команды Dynamic Security, роли устройства и сервера.
- `unzip.mjs` — чтение zip в памяти (stored, deflate) с защитой от zip-бомб: предел записей, суммы распакованного, распаковка не больше заявленного, CRC-32; zip64 и шифрование — отказ.

## `npm run provision:dev`

Только разработка (отказ при `NODE_ENV=production`). Через `MQTT_ADMIN_USER` в Dynamic Security: роль `bl-server` (`bl/v1/#`: подписка, приём, публикация) и клиент `MQTT_SERVER_USER` с паролем из `.env` и закреплённым client id `bl-server` (второе подключение с другим client id брокер отвергает). Для каждого устройства в базе: роль `bl-device-<device_id>` с точными топиками протокола §2 (подписка и приём только своего `cmd`; публикация своих `ack`, `state`, `event`, `status`), клиент с логином и обязательным client id = `device_id`, новый пароль MQTT и новый `device_key`. Ключ пишется в `bl.devices.device_key_enc` (через `DATABASE_ADMIN_URL`), всё вместе — в `deploy/dev/devices.json` (или `SIM_DEVICES_FILE`) с правами 0600; `mqtt_url` и `ca_file` в файле — значения `MQTT_URL` и `MQTT_CA_FILE`.

Запущенный при провижининге симулятор брокер отключает (новый пароль), а его старый ключ дал бы `bad_sig`.
