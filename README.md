# Бильярдум

Платформа для бильярдных клубов России: программа клуба, контроллер света на каждом столе, приложение гостя (PWA и мини-приложения MAX и Telegram), публичный сайт-агрегатор с турнирами и рейтингом.

Что строим: [`docs/PRODUCT.md`](docs/PRODUCT.md). Протокол контроллера: [`docs/protocol.md`](docs/protocol.md). Этапы: [`docs/ROADMAP.md`](docs/ROADMAP.md). Решения: [`docs/decisions.md`](docs/decisions.md). Правила работы: [`CLAUDE.md`](CLAUDE.md).

## Требования

- **Docker** (Engine 25+, Compose v2.20+): Docker Desktop на macOS и Windows, Docker Engine с плагином Compose на Linux.
- **Node 22** или новее (вместе с npm).

Больше ничего не нужно: OpenSSL, Postgres и Mosquitto на машину не ставятся. Фронтенд собирается на хосте тем же Node.

## Быстрый старт

```sh
npm run dev
```

Первый запуск:

1. проверяет Docker и Compose;
2. создаёт `.env` по образцу `.env.example` со случайными паролями и ключами, в том числе парой ключей VAPID для Web Push (значения не выводятся). В уже существующий `.env` дописывает только недостающие переменные;
3. ставит зависимости (`npm ci`), если их ещё нет;
4. создаёт dev-сертификаты брокера в `deploy/dev/certs/` (`scripts/dev-certs.mjs`);
5. поднимает базу и брокер и ждёт их готовности;
6. применяет миграции и сид, создаёт учётные записи брокера и ключи 8 тестовых устройств (`deploy/dev/devices.json`), регистрирует мост ККТ тестового клуба (токен — в `deploy/dev/kkt-bridge.token`);
7. собирает приложение гостя и программу клуба на хосте (`npm run build -w web/guest`, `-w web/admin`);
8. запускает сервер, симулятор контроллеров, эмуляторы ЮKassa и ККТ АТОЛ, мост ККТ и Caddy и показывает логи.

Эмуляторы и мост ККТ запускаются, когда их пакеты уже есть в репозитории; чего не хватает, `npm run dev` пишет в логе.

Когда всё поднялось, в логе сервера появляется строка `{"msg":"devices_online","online":8,"total":8}`.

`Ctrl+C` закрывает логи, окружение продолжает работать.

### После обновления кода

Сервисы Node (`server`, `device-sim`, `yookassa-emu`, `kkt-emu`, `kkt-bridge`) работают из смонтированного репозитория, но процесс держит код, загруженный при старте: после `git pull` или правок работающий контейнер остаётся на старом коде. Поэтому после обновления кода запускайте `npm run dev` ещё раз. Повторный запуск:

- применяет новые миграции (`db:migrate`, всегда) и сид — до перезапуска сервера, так что сервер не опережает схему;
- перезапускает только те сервисы, чей код изменился с их старта, остальные не трогает. Код сервиса — его папки (у `server` ещё `api/`, `shared/`, `supabase/` и `.env`), `package-lock.json`, сертификат CA брокера, а у симулятора и моста ещё и их ключи; тесты и `*.md` не считаются. Отпечаток (sha256 содержимого) запоминается в `deploy/dev/code-state.json` (вне git) по id контейнера и времени его старта. Если записи нет или контейнер с тех пор перезапускался не через `npm run dev`, сравнивается время: файл новее старта контейнера — перезапуск;
- если перезапускается сервер, заново выдаёт ключи устройств (`provision:dev`) и токен моста ККТ, поэтому перезапускаются и симулятор, и мост (контейнер моста — новый). Если сервер не менялся, ключи прежние;
- `db` и `mosquitto` не перезапускает никогда (брокер — только если перевыпущены его сертификаты, например после `DEV_LAN_HOST`); `caddy` — если изменился `deploy/dev/Caddyfile`;
- изменения `compose.yml` и `.env` для контейнеров Compose применяет сам (пересоздаёт контейнер);
- пересобирает фронтенд и показывает логи с начала этого запуска.

Что перезапущено и почему, `npm run dev` пишет в логе и в сводке. Ещё два режима:

```sh
npm run dev -- --check     # ничего не меняет: какие сервисы отстали от кода; код выхода 1 — отстали
npm run dev -- --restart   # перезапустить все сервисы Node и выдать новые ключи, даже если код не менялся
```

`--check` удобно запускать перед ручной проверкой или сценариями приёмки на уже поднятом стенде. В CI стенд разработки не используется: каждый запуск поднимает одноразовые Postgres и брокеры с нуля (раздел «Тесты и проверки»).

Фронтенд собирается на хосте, а не в контейнере: у Vite нативный `esbuild` под платформу хоста, и в Linux-контейнере на macOS и Windows он не запустится. Caddy раздаёт готовые `web/guest/dist` и `web/admin/dist`. Если сборка упала, окружение всё равно поднимается, а `npm run dev` пишет об этом в сводке.

Пересборка на лету, пока правите интерфейс:

```sh
npm run dev -- --watch-web
```

Рядом с логами сервера запускается `vite build --watch` обоих приложений (или скрипт `build:watch` пакета, если он есть). После сохранения файла обновите страницу. `Ctrl+C` останавливает и пересборку.

### Адреса

| Адрес | Что там |
|---|---|
| `https://localhost:8443/app/` | приложение гостя (PWA); стол по QR — `/app/t/{код}` |
| `https://localhost:8443/club/` | программа клуба: ресепшн, владелец, управляющий |
| `https://localhost:8443/pay/{id}` | страница подтверждения оплаты эмулятора ЮKassa (кнопки «Оплатить» и «Отказ») |
| `https://localhost:8443/api/` | API сервера; `/api/stream` — поток событий (SSE) |
| `wss://localhost:8443/api/kkt/ws` | WebSocket моста ККТ (так подключается мост на ПК ресепшена) |
| `https://localhost:8443/t/{код}` | короткая ссылка с QR-наклейки, сервер перенаправляет на `/app/t/{код}` |
| `https://localhost:8443/` | перенаправляет на `/app/` |
| `http://localhost:3000/health` | сервер напрямую, без Caddy |
| `http://127.0.0.1:18080` | управление симулятором контроллеров |

Caddy ставит заголовки безопасности: CSP без внешних источников (скрипты, стили, шрифты, картинки и запросы — только со своего хоста), `X-Content-Type-Options`, `Referrer-Policy: same-origin`, `Permissions-Policy`. HSTS — только не для `localhost` и `127.0.0.1`. Приложение гостя разрешено показывать во фрейме только веб-версиям Telegram и MAX (мини-приложения), программу клуба — никому. `index.html` и `sw.js` браузер перепроверяет при каждом открытии, ассеты с хешем в имени кэшируются на год. Подробности — в [`deploy/dev/Caddyfile`](deploy/dev/Caddyfile).

### Столы и вход для разработки

В сиде клуб в Екатеринбурге и 8 столов с кодами `TEST000001` … `TEST000008` (стол N — `TEST00000N`). Стол открывается так же, как по QR-наклейке: `https://localhost:8443/t/TEST000004` → `/app/t/TEST000004`. Наклейки с QR — в программе клуба (владелец) или `GET /api/clubs/{club}/qr-stickers.pdf`.

С `ALLOW_DEV_LOGIN=1` (по умолчанию в `.env` разработки) работает вход по телефону без бота: в приложении гостя и в программе клуба — кнопка входа по телефону (`npm run dev` собирает их с `VITE_DEV_LOGIN=1`), в API — `POST /api/auth/dev` с `{"phone":"…"}`, ответ `{token, user}`. Токен передаётся в `Authorization: Bearer …` или ставится cookie. При `NODE_ENV=production` маршрута нет вовсе.

| Телефон | Кто |
|---|---|
| `+70000000001` | владелец тестового клуба |
| `+70000000003` | управляющий |
| `+70000000004` | ресепшн |
| любой другой, например `+79990000001` | новый гость (согласие на обработку данных — при первой оплате) |

```sh
curl -sk https://localhost:8443/api/auth/dev -H 'Content-Type: application/json' -d '{"phone":"+79990000001"}'
```

Вход через MAX и Telegram требует токенов ботов (`MAX_BOT_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`) и публичного адреса; без них каналы выключены, а уведомления пишутся в базу со статусом `skipped`.

### Ускоренное время

С `DEV_ALLOW_ANY_MINUTES=1` (по умолчанию в разработке) котировка (`POST /api/quotes`) принимает любое число минут от 1, а не только варианты тарифа. Так сценарии конца игры проходят за минуты, а не часы. Пороги не ускоряются: контроллер предупреждает за 5 и за 1 минуту (`warn_ms` 300 000 и 60 000), уведомления гостю идут по расписанию планировщика, как в бою. Игра на 3 минуты проверяет конец игры и льготу, на 12 — все сигналы. В production флаг не действует.

### Оплата на эмуляторе ЮKassa

Сеть разработки закрыта от `api.yookassa.ru`, поэтому сервер ходит в эмулятор `tools/yookassa-emu/` (`YOOKASSA_API_URL=http://yookassa-emu:8090/v3`). Эмулятор доступен только внутри Docker Compose; браузер открывает его страницу оплаты через Caddy: `https://localhost:8443/pay/{id}`. Кнопка «Оплатить» отправляет вебхук на `http://server:3000/api/webhooks/yookassa/{club_id}`. Магазин эмулятора (`YOOKASSA_EMU_SHOP_ID`, `YOOKASSA_EMU_SECRET`) создаётся в `.env`, `npm run provision:dev` записывает его в настройки тестового клуба. Сервис в профиле Compose `yookassa-emu`: `npm run dev` включает его, когда есть `tools/yookassa-emu/index.mjs`, иначе `/pay/` отвечает 502.

Подтвердить оплату:
- в браузере — кнопка «Оплатить» на `https://localhost:8443/pay/{id}`, куда приложение переводит после «Оплатить»;
- без браузера (тесты) — управлением эмулятора `/__emu/…`. Оно наружу не опубликовано, только изнутри контейнера; `{id}` — платёж ЮKassa из `confirmation.url` (`…/pay/{id}`) ответа `POST /api/quotes/{id}/pay` или из списка `GET /__emu/payments`:

```sh
docker compose -p billiardum exec yookassa-emu wget -qO- --post-data='' http://127.0.0.1:8090/__emu/payments/{id}/succeed
docker compose -p billiardum exec yookassa-emu wget -qO- http://127.0.0.1:8090/__emu/payments     # все платежи
```

Отказ — `…/cancel`, повтор вебхука — `…/webhook?repeat=N`. Остальные команды — в README эмулятора (`tools/yookassa-emu/`).

### Симулятор контроллеров

Сервис `device-sim` поднимает 8 виртуальных контроллеров по `deploy/dev/devices.json`. Управление — по HTTP с этой машины: `http://127.0.0.1:18080` (обрыв связи, перезагрузка, обход реле, неисправная лампа, медленный `ack`, метрики). Список команд — в [`tools/device-sim/README.md`](tools/device-sim/README.md). NVS контроллеров хранится в томе `device-sim-nvs` и переживает перезапуск контейнера.

```sh
docker compose -p billiardum logs -f device-sim     # лог симулятора
docker compose -p billiardum restart device-sim     # все контроллеры перезагрузились
```

### Касса, бар и смены

Всё — в программе клуба `https://localhost:8443/club/` под ресепшеном (`+70000000004`, PIN `1234`) или управляющим (`+70000000003`):

- **Смена.** Сначала открыть смену с разменом (сколько наличных в кассе). Без открытой смены наличные не принимаются (`shift_closed`). Закрыть смену можно только с фактом наличных: система покажет ожидаемую сумму (размен + наличные продажи − наличные возвраты) и расхождение; расхождение не 0 — тревога владельцу сразу. Одна открытая смена на клуб.
- **Касса** «как в магазине»: товары, заявка стола, пакет часов, депозит; оплата наличными (со сдачей), картой через терминал клуба или по СБП (QR на экране, платёж на эмуляторе ЮKassa). Скидка выше лимита клуба (10 %) — только управляющий с причиной, возврат — управляющий или владелец с причиной.
- **Бар.** Заказы со стола (меню в «Игре» у гостя, оплата онлайн или «в счёт стола») и с кассы приходят на экран бара: новый → готовится → готов → выдан. Счёт стола остаётся открытым до оплаты и после конца игры.
- **Склад:** приход, списание, ревизия; остаток — сумма движений.
- **Чек** на каждую оплату на ресепшене пробивает ККТ клуба через мост (ниже). Пока ККТ недоступна, продажа сохраняется со статусом `receipt_pending`, ресепшн видит предупреждение, чек пробивается после включения; не пробит 10 минут — тревога владельцу.

Алкоголь гостю не показывается и не продаётся в QR-меню: сервер скрывает товары с `is_alcohol`, пока в настройках платформы не включено `qr_alcohol_allowed` (только после заключения юриста). На кассе алкоголь продаётся как обычно.

### Эмулятор ККТ АТОЛ

Настоящей ККТ в разработке нет. Сервис `kkt-emu` (`tools/kkt-bridge/emu/`) повторяет веб-сервер драйвера АТОЛ (ДТО 10, HTTP JSON) на порту 16732, как настоящий: принимает задания на чек `POST /api/v2/requests`, отдаёт результат с номером ФД и ФП. Порт открыт только внутри сети Compose: к эмулятору ходит мост ККТ.

Управление для тестов `/__emu/…` наружу не опубликовано, только изнутри контейнера:

```sh
E='docker compose -p billiardum exec kkt-emu wget -qO- --header Content-Type:application/json'
$E http://127.0.0.1:16732/__emu/state                                  # состояние ККТ: смена, бумага, связь
$E http://127.0.0.1:16732/__emu/documents                              # пробитые документы (ФД, ФП, суммы)
$E --post-data='{"on":false}' http://127.0.0.1:16732/__emu/power       # ККТ выключена (T14)
$E --post-data='{"on":true}' http://127.0.0.1:16732/__emu/power        # снова включена
$E --post-data='{"present":false}' http://127.0.0.1:16732/__emu/paper  # кончилась бумага
```

Ещё: ошибка ФН (`/__emu/fn`), задержка (`/__emu/delay`), обрыв после закрытия документа (`/__emu/fault`), смена старше 24 часов (`/__emu/shift`), сброс (`/__emu/reset`); у выключенной ККТ три поведения (`mode`: `reject`, `error`, `wait`) — подробно в `tools/kkt-bridge/README.md` и в шапке `tools/kkt-bridge/emu/emulator.mjs`. Эмулятор держит состояние в памяти: после перезапуска контейнера нумерация ФД начинается заново. Сервис в профиле Compose `kkt-emu`: `npm run dev` включает его, когда есть `tools/kkt-bridge/emu/index.mjs`.

### Мост ККТ в разработке

Сервис `kkt-bridge` — та же служба, что ставится на ПК ресепшена (`tools/kkt-bridge/`): держит исходящее WebSocket-соединение с сервером, получает задания на чек и отправляет их в ККТ (здесь — в эмулятор), сервер получает номер ФД, ФП и время. Задание идемпотентно по `receipt_id`: повтор после обрыва не пробьёт второй чек.

- `npm run dev` после `provision:dev` регистрирует мост тестового клуба: новый токен, когда перезапускается сервер, при `--restart` или если токена нет (в базе — только хеш) в файле `deploy/dev/kkt-bridge.token` (права 0600, вне git, стирается `npm run down -- --volumes`).
- Настройки моста — [`deploy/dev/kkt-bridge.json`](deploy/dev/kkt-bridge.json), без секретов: сервер — напрямую по сети Compose, `ws://server:3000/api/kkt/ws` (`allow_insecure` — только для разработки), ККТ — `http://kkt-emu:16732`, токен — `token_file`, журнал — `/var/lib/kkt-bridge` в контейнере (живёт, пока жив контейнер; при новом токене `npm run dev` создаёт контейнер заново). Память эмулятора живёт, пока не перезапущен его процесс. Не через Caddy: сертификат Caddy выписан на `localhost`, а не на имя контейнера, и мост не должен зависеть от пересоздания Caddy. Путь через Caddy, как на ПК ресепшена, проверяет `npm run ci -- --config`; вручную — мост с хоста ниже.
- Сервис в профиле Compose `kkt-bridge`: стартует, когда есть `tools/kkt-bridge/index.mjs` и токен.

```sh
docker compose -p billiardum logs -f kkt-bridge     # лог моста
docker compose -p billiardum stop kkt-bridge        # мост «выключили» — чеки копятся в receipt_pending
docker compose -p billiardum start kkt-bridge       # мост снова на связи — очередь чеков пробивается
```

Мост с хоста через Caddy — так же, как на ПК ресепшена: `wss://localhost:8443/api/kkt/ws`, настройки [`deploy/dev/kkt-bridge.host.json`](deploy/dev/kkt-bridge.host.json) с тем же токеном, эмулятор АТОЛ — на хосте (`127.0.0.1:16732`), доверие — корень CA Caddy:

```sh
docker compose -p billiardum cp caddy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt
docker compose -p billiardum stop kkt-bridge        # задания должен получать мост с хоста, а не контейнер
npm run emu -w @billiardum/kkt-bridge               # эмулятор АТОЛ на 127.0.0.1:16732 (отдельный терминал)
NODE_EXTRA_CA_CERTS=./caddy-root.crt node tools/kkt-bridge/index.mjs --config deploy/dev/kkt-bridge.host.json
```

Журнал такого моста — `deploy/dev/kkt-bridge-data/` (вне git). Вернуть мост в контейнере: `docker compose -p billiardum start kkt-bridge`. В Caddy маршрут `/api/kkt/ws` отдельный: заголовки `Upgrade` и `Connection` уходят серверу, кадры идут без буфера, простой соединения не обрывается (проверено 330 с: `node scripts/ci-caddy-ws.mjs --idle 330`), перезагрузка конфига Caddy даёт открытым мостам 5 минут (`stream_close_delay`).

### С телефона в локальной сети

Телефон и компьютер — в одной сети Wi-Fi.

1. Узнайте IP компьютера в локальной сети (macOS: `ipconfig getifaddr en0`; Windows: `ipconfig`; Linux: `hostname -I`), например `192.168.1.10`.
2. В `.env` поставьте `DEV_LAN_HOST=192.168.1.10` и `PUBLIC_HOST=192.168.1.10:8443`. Второе нужно, чтобы ссылки QR-наклеек и возврат после оплаты вели на компьютер, а не на `localhost` телефона.
3. Перезапустите: `npm run dev`. Caddy выпустит сертификат и на этот адрес.
4. Установите на телефон корень CA Caddy: скачайте его `docker compose -p billiardum cp caddy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt` и передайте на телефон. iOS: открыть файл → «Настройки» → «Профиль загружен» → установить, затем «Основные» → «Об этом устройстве» → «Доверие сертификатам» → включить. Android: «Настройки» → «Безопасность» → «Шифрование и учётные данные» → «Установить сертификат» → «Сертификат CA». Без этого браузер предупредит о сертификате, а Service Worker и установка PWA не заработают.
5. Откройте `https://192.168.1.10:8443/app/`. Если не открывается — разрешите входящие на порт 8443 в брандмауэре компьютера. На компьютере тоже открывайте этот адрес: ссылки, возврат после оплаты и cookie входа привязаны к `PUBLIC_HOST`.

Мини-приложения Telegram и MAX так не открыть: мессенджерам нужен публичный адрес с настоящим сертификатом.

### Что поднимается

Проект Docker Compose `billiardum`, файл [`deploy/dev/compose.yml`](deploy/dev/compose.yml).

| Сервис | Образ | Адрес на хосте | Что это |

| `db` | `supabase/postgres:15.8.1.085` | `localhost:54322` (только с этой машины) | Postgres с RLS |

| `kkt-emu` | `node:22.23.4-alpine` | — | эмулятор веб-сервера драйвера АТОЛ, порт 16732 внутри сети Compose |
| `kkt-bridge` | `node:22.23.4-alpine` | — | мост ККТ тестового клуба: `ws://server:3000/api/kkt/ws` ↔ `http://kkt-emu:16732` |

## Мост ККТ на ПК ресепшена (настоящая ККТ АТОЛ)

Мост — скрипт на Node 22 с файлом настроек (decisions №85; установщик для Windows — после пилота). Он сам подключается к серверу по `wss://` и забирает задания на чек; на ПК наружу ничего не открывается, нужен только исходящий HTTPS (443) до сервера.

1. **ККТ и драйвер АТОЛ.** ККТ подключена к ПК ресепшена (USB или COM). Установлен драйвер ККТ АТОЛ 10.x (ДТО 10) с веб-сервером; в «Тесте драйвера ККТ» связь с ККТ проверена, веб-сервер работает на `http://127.0.0.1:16732` (порт по умолчанию). Порт 16732 в брандмауэре не открывать: веб-сервер нужен только мосту на этом же ПК.
2. **Node 22.** Установщик Node.js 22 LTS для Windows (x64); проверка в «Командной строке»: `node -v` — `v22.…` или новее.
3. **Файлы моста.** Скопировать папку `tools/kkt-bridge` из репозитория в `C:\kkt-bridge` (папки `emu` и `test` на ПК не нужны). Сторонних пакетов у моста нет: WebSocket и HTTP — встроенные в Node 22.
4. **Токен.** Владелец в программе клуба регистрирует мост этого ПК и получает токен (`POST /api/clubs/{club}/kkt/bridges`; в базе хранится только хеш, токен показывается один раз). Токен — в файл `C:\kkt-bridge\token.txt`, доступ к файлу — только у учётной записи, под которой работает мост. Токен потерян или ПК сменился — владелец отзывает мост и выдаёт новый токен.
5. **Файл настроек** `C:\kkt-bridge\kkt-bridge.json` в кодировке UTF-8 без BOM (в «Блокноте» — «Сохранить как» → «UTF-8»); относительные пути — от папки этого файла:

   ```json
   {
     "server_url": "wss://{адрес сервера}/api/kkt/ws",
     "token_file": "token.txt",
     "atol_url": "http://127.0.0.1:16732",
     "name": "Ресепшн"
   }
   ```

   Ещё: `"atol_api": "legacy"` — для старого веб-сервера ДТО 10 (адреса `/requests` вместо `/api/v2/requests`); `atol_device_id` — если на веб-сервере несколько ККТ; `atol_user` и `atol_password` — если у веб-сервера включён вход; `data_dir` — журнал моста (по умолчанию `kkt-bridge-data` рядом с файлом настроек: UUID отправленных заданий, чтобы повтор после сбоя не пробил второй чек). Вместо `token_file` можно переменную окружения `KKT_BRIDGE_TOKEN`. Образец — `tools/kkt-bridge/kkt-bridge.example.json`, все поля — `tools/kkt-bridge/lib/config.mjs`.
6. **Запуск** в «Командной строке»: `cd C:\kkt-bridge` и `node index.mjs --config kkt-bridge.json`. В логе — подключение к серверу и состояние ККТ; в программе клуба мост виден на связи. Проверка — продажа на кассе: чек печатается, в программе клуба у продажи номер ФД и ФП.
7. **Автозапуск** — «Планировщик заданий» Windows → «Создать задачу»: триггер «При запуске»; действие — программа `C:\Program Files\nodejs\node.exe`, аргументы `index.mjs --config kkt-bridge.json`, рабочая папка `C:\kkt-bridge`; на вкладке «Общие» — «Выполнять для всех пользователей» (запуск при старте ПК, без входа в систему); на вкладке «Параметры» — «При сбое перезапускать через 1 мин» (число попыток — 999), «Останавливать задачу, выполняемую дольше» — снять. Мост не должен завершаться сам: при обрыве связи с сервером или ККТ он переподключается. Планировщик перезапускает задачу только при сбое (код выхода не 0), поэтому выход моста с кодом 0 — ошибка моста. Обновление моста — заменить файлы (кроме `kkt-bridge.json`, `token.txt` и `kkt-bridge-data`) и перезапустить задачу.

Если ККТ выключена или нет бумаги, продажи не теряются: чеки ждут в очереди сервера (`receipt_pending`), ресепшн видит предупреждение, чек пробивается, как только ККТ снова на связи; не пробит 10 минут — тревога владельцу.

## Тесты и проверки

```sh
npm test            # юнит-тесты всех пакетов, без базы и брокера
npm run lint        # ESLint по всему репозиторию
npm run test:db     # тесты на Postgres окружения npm run dev (базы временные, рабочую не трогают)
npm run ci          # как в CI: всё ниже, кроме --pio
npm run ci -- --db  # только этап базы из CI: свой Postgres
```

`npm run test:db` (`scripts/ci-test-db.mjs`) гоняет `test:db` пакетов `@billiardum/db` и `@billiardum/server` (и других пакетов, где этот скрипт есть), тесты light: `LIGHT_IT=1 node --test --test-concurrency=1 "server/test/light/*.test.mjs"` и тесты модулей на базе — каждый каталог `server/test/<модуль>/` (касса, ККТ, смены) и `server/<модуль>/test/db/` по очереди. База — `DATABASE_ADMIN_URL` из окружения или `.env`. Интеграция light + брокер + симулятор (`it-sim`, p95 до `ack`) сама поднимает и удаляет свой брокер `bl-light-it-*` (нужны Docker и `openssl`); брокер `npm run dev` она не трогает. Без неё — `LIGHT_IT=0 npm run test:db`.

| Этап `npm run ci -- …` | Что проверяет |
|---|---|
| `--base` | каждый `*.test.mjs` запускает какой-то скрипт (иначе — ошибка со списком файлов), lint, юнит-тесты всех пакетов (и `@billiardum/kkt-bridge`), `test:it` пакетов, где он есть (симулятор — свой брокер в Docker) |
| `--config` | `docker compose config` со всеми профилями, `caddy validate`, WebSocket `/api/kkt/ws` через Caddy (временная сеть, заглушка сервера: Upgrade, Authorization с токеном моста, кадры без буфера, 3 МБ, простой), `mosquitto --test-config` — образами из `compose.yml` |
| `--web` | сборка `web/guest` и `web/admin`, бюджет JS гостя: `npm run size -w web/guest` (≤ 200 КБ gzip) |
| `--fw` | нативные тесты логики прошивки: CMake + g++ по `firmware/test/native`, `ctest` |
| `--db` | одноразовый Postgres: все миграции (и `0400–0599` кассы и ККТ), сид, `npm run test:db` целиком, включая интеграцию light со своим брокером (нужен `openssl`) |
| `--pio` | `pio run -e esp32dev` и `pio test -e native`; нужен PlatformIO 6.1.19 и доступ к реестру PlatformIO, по умолчанию не входит |

Пакеты, которых ещё нет, пропускаются с сообщением. Для `--fw` нужны CMake 3.20+ и компилятор C++.

`npm run ci` поднимает одноразовые Postgres и брокеры на свободных портах и удаляет их в конце; окружение `npm run dev` не трогает. В GitHub то же делает [`.github/workflows/ci.yml`](.github/workflows/ci.yml) теми же `node scripts/ci.mjs --…`: задачи `ci` (`--base`, `--config`, `--db`), `web` (`--web`), `firmware-native` (`--fw`) и `firmware-pio` (`--pio`, PlatformIO ставится на раннере, версия закреплена). Локально `npm run ci` покрывает всё, кроме `--pio`: реестр PlatformIO в среде разработки закрыт, `--pio` запускается отдельно там, где он доступен. CI работает только с синтетическими данными сида.
