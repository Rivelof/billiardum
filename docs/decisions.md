## 2026-10-21 · оркестратор (шаг 0)

Технические решения в рамках CLAUDE.md. Файлов агентов в стартовом комплекте не было, поэтому решения сверяются с ними, когда файлы появятся. Андрей может отменить любое решение: тогда новая запись со ссылкой.

11. **Supabase — это Postgres с RLS, без публичных сервисов.** Поднимаем образ `supabase/postgres`, Studio только в разработке. PostgREST, GoTrue, Realtime и Storage наружу не публикуются. `api/` ходит в базу через `pg`: каждый запрос выполняется в транзакции с `SET LOCAL ROLE app_api` и идентификаторами пользователя и клуба в настройках сессии, поэтому RLS действует и на сервер. Вход свой: `api/` проверяет `initData` MAX и Telegram и коды в боте и выдаёт токен. *Почему:* инвариант 9 запрещает клиенту ходить в базу, а GoTrue не умеет вход через MAX и коды в мессенджере.
12. **Роли базы.** Таблицами владеет отдельная роль миграций. Рабочая роль `app_api` таблицами не владеет и `BYPASSRLS` не имеет. На всех таблицах с `club_id` включены `ENABLE` и `FORCE ROW LEVEL SECURITY`. *Почему:* владелец таблицы по умолчанию обходит RLS, и изоляция клубов держалась бы на дисциплине кода.
13. **Журнал: своя цепочка хешей у каждого клуба, хеш считает база.** Триггер `BEFORE INSERT` берёт блокировку по клубу (`pg_advisory_xact_lock`), читает `hash` последней записи клуба и записывает `prev_hash` и `hash = sha256(prev_hash || канонические поля записи)`. Приложение хеш не передаёт. Триггеры запрещают `UPDATE`, `DELETE` и `TRUNCATE` всем ролям, включая суперпользователя: RLS он обходит, триггер нет. Записи платформы без клуба идут в отдельную цепочку. Хеш головы цепочки клуба уходит владельцу в утренней сводке. *Почему:* инвариант 2. Отдельная цепочка не заставляет клубы ждать друг друга на вставке и проверяется без чужих данных. Хеш, уже отправленный владельцу, выдаёт даже цепочку, переписанную целиком из-под суперпользователя.
14. **Протокол v0 → v1: правки при утверждении в M0** (вместе с firmware и backend).
    1. Точный повтор команды (тот же `id` и `seq`, протокол §6) получает исходный `ack` без повторного исполнения. `replayed_seq` возвращается только при `seq` меньше сохранённого или равном ему с другим `id`. *Почему:* в v0 §3 и §6 противоречат друг другу: при потерянном `ack` штатный повтор сервера получал бы ошибку.
    2. Канонический JSON задан строго: ключи по алфавиту на всех уровнях, без пробелов, только целые числа, строки UTF-8 без экранирования не-ASCII; подпись считается по байтам UTF-8 и сравнивается за постоянное время. Общие тестовые векторы лежат в `docs/protocol-vectors.json`, прошивка, симулятор и сервер обязаны их проходить. *Почему:* расхождение канонизации в C++ и Node — самая вероятная причина ложных `bad_sig`.
    3. В `ota.start` поле `sig` переименовано в `image_sig`. *Почему:* правило «канонический JSON без поля `sig`» неоднозначно при вложенном `sig`.
    4. Контроллер сообщает `caps` (`relay`, `led`, `buzzer`, `current`, `dimmer`) в `boot` и `state`. *Почему:* протокол одинаков для своей платы и готового реле (PRODUCT §22.1); если датчика тока нет, владелец видит, что защита от света в обход выключена.
    5. В диаграмму состояний добавлены `pending` и `reserved`: по истечении `until_ms` контроллер сам возвращается в `free`, `session.start` принимается из обоих.
    6. Поведение после перезагрузки без сервера (§5, правило 4) — вопрос Андрею, до ответа правило не утверждается.
15. **Доступ устройств к брокеру — Mosquitto Dynamic Security.** При привязке сервер создаёт устройству клиента и роль с точными топиками `bl/v1/{club_id}/{device_id}/`: чтение `cmd`, запись `ack`, `state`, `event`, `status`. Анонимный вход запрещён. Сервер не доверяет `club_id` из топика и сверяет устройство по таблице `devices`. *Почему:* устройства добавляются на ходу, без правки файлов на сервере и без перезапуска брокера, который в часы работы запрещён.
16. **Офлайн и тревога.** Контроллер считается офлайн по Last Will (около 45 с при `keepalive` 30 с) или после 150 с без `state`. Тревога владельцу уходит после 120 с непрерывного офлайна во время сессии. *Почему:* протокол §6 (150 с) и PRODUCT §8 («больше 2 минут») расходились.
17. **Сид: клуб в Екатеринбурге, `Asia/Yekaterinburg` (UTC+5)**, 8 столов (5 пирамида, 3 пул), тарифы из PRODUCT §9. Для тестов изоляции второй клуб в другом часовом поясе создаётся только в тестовых данных. *Почему:* пояс не совпадает ни с UTC, ни с Москвой, поэтому ошибки местного времени видны сразу.
18. **Таблица `tariff_rules` создаётся в M0** (схема и сид), движок тарифов — в M1. *Почему:* сид M0 требует тарифы, а в списке миграций M0 их нет.
19. **Папки вне карты CLAUDE.md:** `deploy/dev/` — Docker Compose для разработки (devops), `.github/workflows/` — CI (devops), `tests/e2e/` — сценарии tester, `docs/protocol-vectors.json` и `docs/contracts/` — оркестратор.
20. **Запуск одной командой — `npm run dev`** (npm workspaces), внутри Docker Compose. *Почему:* одинаково работает на macOS, Windows и Linux; `make` на Windows нет.
21. **CI и среды разработки работают только с синтетическими данными сида.** Дамп боевой базы в разработку, CI и чаты агентов не попадает. *Почему:* раннеры GitHub и облачные среды разработки находятся вне РФ (инвариант 6).
22. **Шрифты и статика — только со своего сервера**, без Google Fonts и внешних CDN. Уточняет DESIGN.md §3. *Почему:* внешний CDN получает IP-адрес каждого гостя; это риск по 152‑ФЗ и запрет CLAUDE.md на сервисы, передающие данные гостей за рубеж.
23. **Секреты устройств и клубов шифруются в приложении.** `device_key` и ключи ЮKassa хранятся в базе в AES-256-GCM, ключ шифрования только в `.env`. *Почему:* дамп базы без `.env` не позволяет подписать команду свету или провести платёж от имени клуба.
24. **Ручные действия — полный список из PRODUCT §8.4.** К списку инварианта 8 в CLAUDE.md добавляются «продление без оплаты» и «изменение тарифа». *Почему:* списки расходились, по продукту главнее docs.
25. **MAX-бот в минимальном виде переезжает в M1:** код входа для PWA и тревоги владельцу. Цепочка каналов с запасным остаётся в M3. *Почему:* ROADMAP M1 требует вход по коду и тревоги в MAX, а бот по плану появлялся только в M3.
26. **«Без лимита» по СБП — автопродление блоками по 30 минут** с подтверждением гостя (запасной вариант PRODUCT §3), заморозка суммы только для карты. Проверить тестовым платежом ЮKassa в M1. *Почему:* по смежной документации Яндекс Пэй оплата по СБП списывается сразу, без стадии блокировки; прямого подтверждения в документации ЮKassa пока нет.

## 2026-10-21 · оркестратор (M0)

31. **Строки в командах — только печатный ASCII без `"` и `\`.** Уточняет №14.2. Причины и типы передаются кодами (`reason_code`), свободный текст причины хранится только в журнале на сервере. Команда с другим символом, дробным числом или числом вне ±(2^53−1) отвергается кодом `bad_format`. *Почему:* одинаковая канонизация в C++ и Node без таблиц экранирования.
32. **Тихие часы пищалки решает сервер.** `session.start`, `session.extend` и `session.resume` несут флаг `buzzer`; в `config.set` тихих часов нет. *Почему:* у контроллера нет надёжных часов и часового пояса клуба, а сервер знает и то и другое.
33. **События контроллера идемпотентны:** каждое несёт `boot` (счётчик перезагрузок) и `n` (номер события после загрузки); сервер пишет событие в журнал один раз по `(device_id, boot, n)`. *Почему:* события из кольцевого буфера досылаются после восстановления связи и могут прийти повторно.
34. **Наши объекты базы — в схеме `bl`, у ролей Supabase на неё нет прав.** *Почему:* в образе `supabase/postgres` 15.8.1.085 роли `postgres`, `service_role`, `supabase_read_only_user` имеют `BYPASSRLS`, `authenticator` может переключаться в `service_role`, а таблицам в `public` Supabase по умолчанию раздаёт права этим ролям. В `public` изоляция клубов держалась бы на пароле одной служебной роли.
35. **Ночные интервалы и праздники в тарифах — семантика в M1.** В M0 таблица `tariff_rules` хранит дни недели и интервалы местного времени; к какому дню относится интервал 00:00–06:00 (календарный или «рабочие сутки клуба») решается вместе с движком тарифов. *Почему:* от этого зависит цена ночи с воскресенья на понедельник и с четверга на пятницу, а движок — задача M1.
36. **Цвета DESIGN.md подправлены до WCAG AA.** Светлая тема: `--ink-3` `#7A869A` → `#616C7F`, `--free` `#1E8E5A` → `#1A7A4D`, `--ball-red` `#D2392C` → `#C6362A`. Тёмная: `--ink-3` `#6E7A90` → `#7E899C`, `--cloth` `#4C82E8` → `#5186E9`. Новые токены `--on-cloth` (светлая `#FFFFFF`, тёмная `#0B1019`), `--on-lamp` (`#0C1424`) и `--line-strong` для полей ввода (светлая `#7A869A`, тёмная `#677387`, ≥ 3:1). *Почему:* DESIGN §2 требует AA для обоих наборов, а тест контраста frontend показал 3,1–4,4:1 у подписей, «свободно», тревог и белого текста на тёмной кнопке. Оттенки сдвинуты минимально, идея «Свет над столом» не меняется. Андрей может отменить: решение принято в рамках «делай всё», DESIGN.md без него не меняется.
37. **Протокол v1 утверждён** с правками по ревью firmware и backend: `clean session = true`; предельные размеры сообщений; строгий JSON (повторяющиеся ключи, любое экранирование и `-0` — `bad_format`); обязательные поля с форматами (`id` — UUID, `seq` ≥ 1, `issued_at` обязателен, `body` — объект); `sig` ровно 44 символа; новый код `bad_body` (с ним `seq` считается принятым); `ack` с `cmd_id: null` на неразобранную команду; одна неподтверждённая команда на устройство, без повторов офлайн; после возвращения онлайн — актуальное состояние, а не старые команды; сверка `seq` по `state.last_seq` с записью `device.seq_sync`; `boot_id` для учёта событий; буфер событий на 64 и ограничение частоты `bad_sig`/`replayed_seq`; сигналы по пересечению порога; уточнения правила 4. Векторов 38. *Почему:* обе стороны независимо нашли одни и те же дыры; без правок были бы лишнее время после офлайна, ложные `replayed_seq` после восстановления базы и потеря событий после замены контроллера.
38. **Защита журнала в базе (backend, M0):** триггеры `ENABLE ALWAYS` (режим `replica` их не отключает: supautils разрешает его роли `postgres`); событийные триггеры против DDL над журналом в отдельной схеме `bl_guard` у суперпользователя; хеш — встроенная `sha256`; у всех, кроме суперпользователей, отозваны `pg_read_all_data` и `pg_write_all_data`; роль `bl_definer` для узких функций поиска устройства. *Почему:* проверено тестами на образе Supabase; каждая мера закрывает найденный обход.
