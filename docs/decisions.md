## 2026-10-21 · оркестратор (шаг 0)

Технические решения в рамках CLAUDE.md. Файлов агентов в стартовом комплекте не было, поэтому решения сверяются с ними, когда файлы появятся. Андрей может отменить любое решение: тогда новая запись со ссылкой.

11. **Supabase — это Postgres с RLS, без публичных сервисов.** Поднимаем образ `supabase/postgres`, Studio только в разработке. PostgREST, GoTrue, Realtime и Storage наружу не публикуются. `api/` ходит в базу через `pg`: каждый запрос выполняется в транзакции с `SET LOCAL ROLE app_api` и идентификаторами пользователя и клуба в настройках сессии, поэтому RLS действует и на сервер. Вход свой: `api/` проверяет `initData` MAX и Telegram и коды в боте и выдаёт токен. *Почему:* инвариант 9 запрещает клиенту ходить в базу, а GoTrue не умеет вход через MAX и коды в мессенджере.
12. **Роли базы.** Таблицами владеет отдельная роль миграций. Рабочая роль `app_api` таблицами не владеет и `BYPASSRLS` не имеет. На всех таблицах с `club_id` включены `ENABLE` и `FORCE ROW LEVEL SECURITY`. *Почему:* владелец таблицы по умолчанию обходит RLS, и изоляция клубов держалась бы на дисциплине кода.
13. **Журнал: своя цепочка хешей у каждого клуба, хеш считает база.** Триггер `BEFORE INSERT` берёт блокировку по клубу (`pg_advisory_xact_lock`), читает `hash` последней записи клуба и записывает `prev_hash` и `hash = sha256(prev_hash || канонические поля записи)`. Приложение хеш не передаёт. Триггеры запрещают `UPDATE`, `DELETE` и `TRUNCATE` всем ролям, включая суперпользователя: RLS он обходит, триггер нет. Записи платформы без клуба идут в отдельную цепочку. Хеш головы цепочки клуба уходит владельцу в утренней сводке. *Почему:* инвариант 2. Отдельная цепочка не заставляет клубы ждать друг друга на вставке и проверяется без чужих данных. Хеш, уже отправленный владельцу, выдаёт даже цепочку, переписанную целиком из-под суперпользователя.
14. **Протокол v0 → v1: правки при утверждении в M0** (вместе с firmware и backend).
    1. Точный повтор команды (тот же `id` и `seq`, протокол §6) получает исходный `ack` без повторного исполнения. `replayed_seq` возвращается только при `seq` меньше сохранённого или равном ему с другим `id`. *Почему:* в v0 §3 и §6 противоречат друг другу: при потерянном `ack` штатный повтор сервера получал бы ошибку.
    2. Канонический JSON задан строго: ключи по алфавиту на всех уровнях, без пробелов, только целые числа, строки UTF-8 без экранирования не-ASCII; подпись считается по байтам UTF-8 и сравнивается за постоянное время. Общие тестовые векторы лежат в `docs/protocol-vectors.json`, прошивка, симулятор и сервер обязаны их проходить. *Почему:* расхождение канонизации в C++ и Node — самая вероятная причина ложных `bad_sig`.
    3. В `ota.start` поле `sig` переименовано в `image_sig`. *Почему:* правило «канонический JSON без поля `sig`» неоднозначно при вложенном `sig`.
    4. Контроллер сообщает `caps` (`relay`, `led`, `buzzer`, `current`, `dimmer`) в `boot` и `state`. *Почему:* протокол одинаков для своей платы и готового реле (PRODUCT §22.1); если датчика тока нет, владелец видит, что защита от света в обход выключена.
    5. В диаграмму состояний добавлены `pending` и `reserved`: по истечении `until_ms` контроллер сам возвращается в `free`, `session.start` принимается из обоих.
    6. Поведение после перезагрузки без сервера (§5, правило 4) — вопрос Андрею, до ответа правило не утверждается.
15. **Доступ устройств к брокеру — Mosquitto Dynamic Security.** При привязке сервер создаёт устройству клиента и роль с точными топиками `bl/v1/{club_id}/{device_id}/`: чтение `cmd`, запись `ack`, `state`, `event`, `status`. Анонимный вход запрещён. Сервер не доверяет `club_id` из топика и сверяет устройство по таблице `devices`. *Почему:* устройства добавляются на ходу, без правки файлов на сервере и без перезапуска брокера, который в часы работы запрещён.
16. **Офлайн и тревога.** Контроллер считается офлайн по Last Will (около 45 с при `keepalive` 30 с) или после 150 с без `state`. Тревога владельцу уходит после 120 с непрерывного офлайна во время сессии. *Почему:* протокол §6 (150 с) и PRODUCT §8 («больше 2 минут») расходились.
17. **Сид: клуб в Екатеринбурге, `Asia/Yekaterinburg` (UTC+5)**, 8 столов (5 пирамида, 3 пул), тарифы из PRODUCT §9. Для тестов изоляции второй клуб в другом часовом поясе создаётся только в тестовых данных. *Почему:* пояс не совпадает ни с UTC, ни с Москвой, поэтому ошибки местного времени видны сразу.
18. **Таблица `tariff_rules` создаётся в M0** (схема и сид), движок тарифов — в M1. *Почему:* сид M0 требует тарифы, а в списке миграций M0 их нет.
19. **Папки вне карты CLAUDE.md:** `deploy/dev/` — Docker Compose для разработки (devops), `.github/workflows/` — CI (devops), `tests/e2e/` — сценарии tester, `docs/protocol-vectors.json` и `docs/contracts/` — оркестратор.
20. **Запуск одной командой — `npm run dev`** (npm workspaces), внутри Docker Compose. *Почему:* одинаково работает на macOS, Windows и Linux; `make` на Windows нет.
21. **CI и среды разработки работают только с синтетическими данными сида.** Дамп боевой базы в разработку, CI и чаты агентов не попадает. *Почему:* раннеры GitHub и облачные среды разработки находятся вне РФ (инвариант 6).

162. **Заводской реестр `bl.device_factory`** хранит только хеш кода привязки; таблица без прав у `app_api`, проверка — узкая функция. В проде (`NODE_ENV=production`) привязываются только устройства из реестра; в разработке и тестах — и без реестра (сид, симулятор). *Почему:* поддельный контроллер с выдуманным `device_id` не должен попасть в клуб.
163. **Цена тарифа — строго больше нуля.** Бесплатная игра — только ручным действием с причиной и уведомлением владельцу (инвариант 8), а не тарифом 0 ₽. *Почему:* находка pentester Н-1 M5.1 — нулевой тариф обходил бы ручное действие «бесплатная игра».
164. **Смена типа стола в `live` — ручное действие** с причиной и уведомлением владельцу (как изменение тарифа): при тарифах по типам столов она меняет цену стола. Позиция на плане — только журнал. *Почему:* вопрос tester Д3 M5.1, инвариант 8.
165. **Приостановленный клуб, который был боевым, считается боевым** для ручных действий (тип и вывод стола, тарифы, магазин): причина обязательна, уведомление владельцу. Общая функция `isLiveClub`. *Почему:* находка pentester П-2 M5.1.
166. **Дашборд владельца — раздел программы клуба** (`docs/contracts/m5-2.md`): видят владелец и управляющий (только свои клубы), ресепшн и бар — нет; экспорт — только владелец; у владельца нескольких клубов — сводка «Все мои клубы»; главный экран владельца — дашборд. *Решение Андрея сделать дашборд по образцу LANGAME; состав — оркестратор.*
167. **Цифры дашборда — по местному времени и рабочим суткам клуба** (`day_start_local`), игра относится к суткам по началу; записи `is_test` не учитываются.
168. **Источник истины дашборда — те же данные, что у отчёта смены и утренней сводки;** выручка за сутки обязана совпадать с ними до копейки, возврат уменьшает выручку в день возврата.
169. **Закрытые сутки — в агрегатах `stats_daily` и `stats_hourly`** (пересчёт планировщиком, в том числе после поздних возвратов и исправлений), текущие сутки — на лету; агрегаты под RLS, пишет только узкая функция.
170. **Загрузка = сыграно / ёмкость,** ёмкость = столы в работе × часы работы клуба (по умолчанию 24); нереализовано = ёмкость − сыграно − сервис.
171. **Гости на дашборде — только количества;** новый — первая игра или бронь в клубе, повторный — была игра раньше, потерянный — 3+ игры и нет 60 дней; экспорт без телефонов и имён гостей.
172. **Экспорт — CSV (UTF-8 с BOM, `;`, ДД.ММ.ГГГГ)** для Excel на русской Windows; журнал `owner.export`.
173. **Экраны истории в программе клуба:** заказы гостей, ревизии, списания, приходы — с диапазоном дат, клубом, поиском, CSV и печатью A4 (PDF — через печать браузера); гость в истории — только маска телефона или ник. *По скриншотам LANGAME от Андрея, `docs/contracts/m5-2.md` §7.*
174. **Ведомость ревизии для печати** с колонкой «факт», по выбору «слепая» (без остатка по системе).
175. **Истории только читают журнал и склад;** правок задним числом нет (инвариант 2).
176. **Список смен с фильтрами** (даты, сотрудник, статус), экспорт и печать; строка открывает отчёт смены.
177. **Касса управляющего — управленческая денежная книга:** инкассации из смен автоматически, прочие доходы и расходы вручную по статьям; записи не правятся, только сторно с причиной; на дашборде «Расходы» и «Прибыль = выручка − расходы» (не бухгалтерия).
178. **Реакция на тревоги в «Контроле»:** время до «принято» по видам и сотрудникам, выделение > 10 мин.
179. **«Кто играл за столом»** для разбора происшествий: гость маской или ником; полный телефон — только владельцу по кнопке с причиной, журнал `guest.lookup` и уведомление владельцу.
180. **Цены подписки платформы — в базе, меняет Андрей;** старт — план «Клуб» 790 ₽ за стол в работе в месяц, персональная цена клуба — с причиной. `docs/contracts/m5-3.md`.
181. **Пробный период подписки — 60 дней с перехода в `live`;** клубы в `test` не платят.
182. **Счёт подписки — раз в месяц вперёд** в день перехода в `live`: столы в работе на дату счёта × цена, без перерасчёта внутри месяца.
183. **Оплата подписки — автоплатежи на магазин ЮKassa платформы** (отдельный от денег гостей, ключи только в `.env`, свой вебхук с перепроверкой); юрлицу по счёту — ручная отметка Андреем с причиной.
184. **Неоплата ничего не отключает автоматически:** повторы через 1 и 3 дня, плашка «Оплаченный период истекает через N дней», через 14 дней — уведомление Андрею, приостановка — только его решением; свет и игры не трогаются никогда (инвариант 3).
185. **Экран «Подписка» — владельцу;** управляющему — только состояние и плашка.
186. **«Клубы и подписки» — Андрею:** состояние, долг, MRR, ручная оплата, персональная цена; оператор — только чтение.
187. **Уточнение №167–169 (по отчёту backend M5.2).** Игра (количество) относится к суткам начала — везде: дашборд, утренняя сводка, отчёт смены. Часы игры и загрузка — по фактическим минутам внутри каждых суток — тоже везде (тепловая карта считается так же). Деньги совпадают всегда. Отчёты смен покрывают сутки, только если смены покрывают все оплаты: ночная оплата по QR без открытой смены есть в дашборде и сводке, но не в отчёте смены — это не расхождение. «Грязные» сутки отмечает триггер (`bl.stats_dirty`), пересчёт — планировщиком. Инкассация — наличные при закрытии смены минус размен, по дню закрытия. Сторно — днём сторно. Поставщик в приходах — в бэклог.
188. **Уточнения подписки (по отчёту backend-billing M5.3).**
    - День счёта — день окончания пробного периода (31-е → последний день месяца).
    - Плашка «истекает через N дней» — только без настроенного автоплатежа; при неуспешной оплате — всегда.
    - Email для чека владелец указывает при первой привязке карты.
    - Привязка карты без счёта — заморозка 1 ₽ с отменой.
    - Ключ идемпотентности — на счёт и номер попытки.
    - Без ключей платформы API подписки отвечает 503 `billing_unavailable`.
    - Двойная оплата одного счёта — счёт закрывается один раз, Андрею уведомление, возврат вручную.
    - Ручная отметка оплаты — только по выставленному счёту.
    - **За время приостановки клуба счета не выставляются и не начисляются задним числом:** после возобновления следующий счёт — с даты возобновления.
    - Магазин ЮKassa клуба не может совпадать с магазином платформы.
