# Прод «Бильярдума»: регламент

Как поднять, обновить, откатить и восстановить прод. Конфиги — `deploy/prod/`, чек-лист пилота — [`PILOT-CHECKLIST.md`](PILOT-CHECKLIST.md).

**Правила, которые нельзя нарушать** (CLAUDE.md):

- Выпуск в прод — только после явного «да» Андрея. Прошивка в клубе — отдельное «да», по одному столу и только на свободных столах.
- Mosquitto не перезапускается в часы работы клубов. База тоже: без неё не стартуют игры.
- Данные гостей — только на серверах в РФ: сервер, бэкапы, логи.
- Секреты — только в `/etc/billiardum/prod.env`. В чат, тикеты и логи — только длина.

## 1. Что где

```
Интернет ──443──▶ caddy ──server-web──▶ server ──db──▶ db (Postgres, без портов)
         │          └────site-web──▶ site ──site-api──▶ server
         └─8883─▶ mosquitto ◀──edge-mqtt── server
```

| Сервис | Образ | Наружу | Что делает |
|---|---|---|---|
| `caddy` | `caddy:2.11.7-alpine@sha256:…` | 443 | TLS Let's Encrypt, `/api/` и `/t/` → server, `/app/` и `/club/` → статика из тома `web-static`, остальное → site |
| `server` | `billiardum-app:<sha>` | — | API, мост MQTT, планировщик, уведомления |
| `site` | `billiardum-app:<sha>` | — | публичный сайт, только через Caddy |
| `db` | `supabase/postgres:15.8.1.085@sha256:…` | — | Postgres с RLS, архив WAL; сети `db` без выхода наружу |
| `mosquitto` | `eclipse-mosquitto:2.1.2-alpine@sha256:…` | 8883 | MQTT по TLS, Dynamic Security, анонимный вход запрещён |
| `migrate`, `web-publish`, `tools` | `billiardum-app:<sha>` | — | разовые команды выпуска, профиль `release` |

Эмуляторов ЮKassa и АТОЛ, симулятора, моста ККТ, сида и входа для разработки в проде нет. Это проверяет `scripts/ci-prod-config.test.mjs` на каждом прогоне CI. Сервисы Supabase, кроме самого Postgres, не запускаются (decisions №11).

| На сервере | Что |
|---|---|
| `/opt/billiardum` | git checkout репозитория, рабочая копия без правок |
| `/etc/billiardum/prod.env` | настройки и секреты, root, `0600` (образец — `deploy/prod/.env.prod.example`) |
| `/etc/billiardum/mqtt/` | `ca.crt`, `mqtt.crt`, `mqtt.key` брокера; `ca.key` здесь не хранится никогда |
| `/var/lib/billiardum/` | `wal-archive/`, `wal-outgoing/`, `backup/`, `monitor/`, `factory/`, `releases.log` |
| `deploy/prod/bin/` | `compose.sh`, `deploy.sh`, `rollback.sh`, `preflight.sh`, `infra-restart.sh`, `caddy-reload.sh`, `mqtt-reload.sh`, `mqtt-certs.sh`, `gen-env.sh` |
| `deploy/prod/backup/`, `monitor/`, `systemd/` | бэкапы, монитор, таймеры |

`docker compose` вызывается только через `deploy/prod/bin/compose.sh`. Обёртка подставляет файл настроек и проект `billiardum-prod` и не даёт вне окна обслуживания команды, которые перезапустят `db` или `mosquitto` (§5.5).

## 2. Требования к серверу в РФ

| Что | Требование |
|---|---|
| Размещение | ЦОД физически в РФ. Проверяется **по договору и документам хостинга** (адрес ЦОД, юрисдикция), а не по названию тарифа или региона в панели |
| 152‑ФЗ | хостинг подписывает поручение на обработку ПДн (ст. 6 ч. 3) или оферту с ним. Адрес ЦОД — в уведомлении Роскомнадзора (PRODUCT §18) |
| Ресурсы на пилот | 2 vCPU, 4 ГБ ОЗУ, 60 ГБ SSD/NVMe, статический IPv4 (IPv6 — по возможности) |
| ОС | Ubuntu 24.04 LTS |
| Сеть | входящие 443/tcp и 8883/tcp для всех, 22/tcp только с адресов администратора. Исходящие: 443 (ЮKassa, Let's Encrypt, npm и Docker Hub при сборке, хранилище бэкапов, прокси Telegram) |
| Время | chrony или systemd-timesyncd, часы синхронизированы (TLS, подписи, сроки броней) |
| Бэкапы | хранилище S3 у **другого** провайдера в РФ (Yandex Object Storage, Selectel, VK Cloud), тоже с ЦОД в РФ по договору |
| Мониторинг снаружи | второй маленький сервер в РФ у другого провайдера, если Андрей согласится (§6.4) |

Бюджет простоя при доступности 99,5 % в месяц (PRODUCT §20) — 3 ч 39 мин.

Порт 80 наружу не открывается: сертификат Let's Encrypt выпускается проверкой TLS-ALPN-01 на 443. Поэтому адрес `http://` не перенаправляется на https, а QR-наклейки и ссылки всегда `https://`.

## 3. Домен и DNS

Домен выбирает Андрей (PRODUCT §22.6). Записи:

| Имя | Тип | Значение | TTL |
|---|---|---|---|
| `{домен}` | A (и AAAA) | IP сервера | 300 |
| `mqtt.{домен}` | A (и AAAA) | IP сервера | 300 |

Брокер получает отдельное имя: адрес выдаётся контроллеру при привязке (`MQTT_PUBLIC_URL`). Если сервер переедет, достаточно поменять запись DNS, контроллеры перепрошивать не нужно. TTL 300 нужен, чтобы при переезде DNS обновился за 5 минут (§7.5). Записи CAA — `0 issue "letsencrypt.org"`.

## 4. Первая установка

Делает devops, когда Андрей сказал «да» на установку. Пока на сервер не смотрит ни один клуб, ограничений по времени нет.

### 4.1. Пакеты и Docker

```sh
apt install -y ca-certificates curl git age rclone openssl chrony
# Docker Engine и плагин Compose — из репозитория Docker (docs.docker.com/engine/install/ubuntu)
apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
```

`/etc/docker/daemon.json` — до первого запуска контейнеров:

```json
{
  "live-restore": true,
  "userland-proxy": false,
  "log-driver": "json-file",
  "log-opts": { "max-size": "20m", "max-file": "10" }
}
```

- `live-restore` — обновление или перезапуск самого Docker не останавливает контейнеры. Без этого `apt upgrade docker-ce` перезапустит брокер в часы работы.
- `userland-proxy: false` — Caddy и брокер видят настоящие адреса клиентов, в том числе по IPv6. Это нужно для лимитов по IP.

Затем `systemctl restart docker`: контейнеров ещё нет. Автообновления (`unattended-upgrades`) — только безопасность. Пакеты `docker-*`, `containerd.io` и ядро исключаются и ставятся вручную в окне обслуживания. Перезагрузка — тоже только в окне.

Межсетевой экран (`ufw` или nftables): 22 — только с адресов администратора, 443 и 8883 — всем. Docker публикует только 443 и 8883, база портов не имеет.

### 4.2. Код и папки

```sh
git clone https://github.com/<org>/billiardum.git /opt/billiardum   # только чтение (deploy key)
install -d -m 700 /etc/billiardum /etc/billiardum/mqtt
install -d -m 755 /var/lib/billiardum
install -d -m 700 /var/lib/billiardum/wal-archive /var/lib/billiardum/wal-outgoing /var/lib/billiardum/backup
install -d -m 700 -o 1000 -g 1000 /var/lib/billiardum/factory          # uid node в образе
```

### 4.3. Настройки

```sh
/opt/billiardum/deploy/prod/bin/gen-env.sh            # /etc/billiardum/prod.env, секреты случайные
nano /etc/billiardum/prod.env                          # домен, бот, прокси, хранилище, ключи age, chat id
/opt/billiardum/deploy/prod/bin/preflight.sh --env-only
```

`gen-env.sh` печатает только длины созданных секретов. Что заполнить руками — комментарии в образце `deploy/prod/.env.prod.example`. Главное:

- `TRUSTED_PROXY_CIDRS`, `PUBLIC_API_TRUSTED_CIDRS`, `SITE_TRUSTED_PROXIES` — конкретные адреса Caddy и сайта `/32`, уже заданные в образце (decisions №70). Если подсети пересекаются с сетью хостинга, они меняются вместе с адресами. `preflight.sh` проверяет, что списки совпадают с адресами.
- **Ключи магазинов ЮKassa клубов здесь не задаются.** Их вводит владелец клуба в мастере, в базе они хранятся зашифрованными `SECRETS_ENC_KEY`. Здесь только магазин платформы для подписки (`PLATFORM_YOOKASSA_*`, M5.3).
- `SECRETS_ENC_KEY` создаётся один раз. Его копию Андрей хранит офлайн (§7.4): без ключа не расшифровать ключи контроллеров и магазинов клубов.
- `YANDEX_METRIKA_ID` — номер счётчика, только для сайта (№141).
- `BACKUP_AGE_RECIPIENTS` — открытый ключ проверки восстановления (его добавляет `gen-env.sh`) и ключ Андрея. Андрей создаёт свой ключ у себя (`age-keygen -o andrey.agekey`), закрытый ключ хранит офлайн, на сервер передаёт только `age1…`. Тот же открытый ключ идёт в `BACKUP_ENV_AGE_RECIPIENT`.

### 4.4. Сертификаты брокера

CA платформы закреплён в прошивке (протокол §2), поэтому создаётся **один раз и не на сервере**, а на доверенном ноутбуке Андрея:

```sh
deploy/prod/bin/mqtt-certs.sh init-ca ~/billiardum-ca                         # ca.key под паролем, ca.crt на 20 лет
deploy/prod/bin/mqtt-certs.sh issue ~/billiardum-ca ./mqtt-out mqtt.{домен}  # mqtt.key, mqtt.crt на 5 лет
scp ./mqtt-out/{ca.crt,mqtt.crt,mqtt.key} root@сервер:/etc/billiardum/mqtt/
```

На сервере: `chmod 600 /etc/billiardum/mqtt/mqtt.key`. `ca.key` и пароль к нему остаются у Андрея: ноутбук и резервная копия офлайн. `ca.crt` нужен прошивке (`kMqttCaPem`, PILOT-CHECKLIST §5).

### 4.5. Первый запуск

```sh
cd /opt/billiardum
deploy/prod/bin/preflight.sh                                       # всё, включая сертификаты и Docker
# db и mosquitto: в окне обслуживания; до пилота, пока клубов нет, — BL_EMERGENCY=1 и слово АВАРИЯ
deploy/prod/bin/compose.sh up -d --no-deps --wait db mosquitto
deploy/prod/bin/deploy.sh <тег>                                    # сборка, миграции, брокер, статика, server, site
deploy/prod/bin/compose.sh up -d --no-deps --wait caddy
```

- Первый `deploy.sh` делает дамп пустой базы, затем применяет все миграции. Сид в прод не попадает: `supabase/seed.sql` не входит в образ, сервиса сида нет.
- `deploy.sh` при каждом выпуске запускает `mqtt-server-client.mjs --if-missing`. Если клиента ещё нет, скрипт создаёт роль `bl-server` и клиента сервера в Dynamic Security на ходу, без перезапуска брокера. Работающего клиента он не трогает. Без этого клиента `server` не станет healthy.
- Caddy получает сертификат при первом запросе к домену. DNS из §3 уже должен смотреть на сервер.

Проверка: `curl -fsS https://{домен}/health`, `compose.sh ps` (все `healthy`), `compose.sh logs --since 5m server` без `config_error`.

### 4.6. Роль Андрея и заводской реестр

1. Андрей входит в программу клуба через Telegram-бота (`/club/`). После первого входа ему выдаётся роль платформы. Телефон набирается на сервере и в лог не пишется:

   ```sh
   deploy/prod/bin/compose.sh exec -T db psql -U supabase_admin -h 127.0.0.1 -d postgres \
     -c "insert into bl.platform_members (user_id, role) select id, 'platform_admin' from bl.users where phone = '+7…' on conflict (user_id) do update set role = 'platform_admin', active = true"
   ```

   Без этого заявки клубов, переход клуба в боевой режим и подписки не уведомляют Андрея (№134, №160).
2. Заводской реестр контроллеров (№159, №162) — только с сервера, база наружу не открыта:

   ```sh
   deploy/prod/bin/compose.sh run --rm tools node scripts/provision-factory.mjs --count 8 --batch P-2026-11 \
     --out /out/factory-P-2026-11.pdf --commands-out /out/factory-P-2026-11.txt
   scp root@сервер:/var/lib/billiardum/factory/factory-P-2026-11.* ./      # на машину сборки
   shred -u /var/lib/billiardum/factory/factory-P-2026-11.*                # на сервере не храним
   ```

   PDF и команды содержат коды привязки в открытом виде. Они не попадают в чат, git и бэкапы.

### 4.7. Бот Telegram

```sh
deploy/prod/bin/compose.sh run --rm tools node server/bin/telegram-webhook.mjs
```

Команда регистрирует вебхук `https://{домен}/api/bots/telegram/webhook` с секретом через `TELEGRAM_PROXY_URL`. Прокси — HTTPS CONNECT или SOCKS5: он видит только адрес `api.telegram.org`, не содержимое. Прокси нужен, потому что с сервера в РФ `api.telegram.org` закрыт.

## 5. Выпуски

### 5.1. Обычный выпуск

Условия: CI зелёный на этом коммите, tester и pentester приняли этап, **Андрей сказал «да»**, есть план отката (§5.4).

```sh
cd /opt/billiardum && deploy/prod/bin/deploy.sh v2026.11.1
```

Что делает `deploy.sh`:

1. Запускает `preflight.sh` и `git checkout`.
2. Собирает образ `billiardum-app:<sha>`. Предыдущий образ остаётся для отката.
3. Делает логический дамп базы в `predeploy/`.
4. Применяет миграции и `reserved-roles.sh`.
5. Кладёт статику в том `web-static`. Ассеты прошлых выпусков хранятся 14 дней: открытые вкладки догружают свои файлы.
6. Пересоздаёт `server` и `site` с `--no-deps --wait`.
7. Если изменился Caddyfile, делает `caddy reload`.
8. Проверяет `/health`, пишет в `releases.log` и сообщает Андрею.

Простой — секунды, пока перезапускается `server`. Пока он перезапускается:

- идущие и оплаченные игры доигрываются на контроллерах (инвариант 3);
- новые игры по QR и оплаты ждут;
- вебхуки ЮKassa повторяются самой ЮKassa;
- мост ККТ и мост MQTT переподключаются сами.

Два экземпляра сервера одновременно не запускаются: у моста MQTT закреплён client id `bl-server` (протокол §2), а outbox слушает одну базу. Поэтому выпуск идёт без простоя на уровне контроллеров, но с секундами простоя API. Выпуски лучше делать в окно наименьшей загрузки, утром.

`db`, `mosquitto` и `caddy` при выпуске не пересоздаются. Если в выпуске изменились их настройки или образ, `deploy.sh` напоминает об этом, а применяет их §5.3.

### 5.2. Миграции

- Каждая миграция должна быть совместима со **старым** кодом, потому что откат кода не откатывает схему (§5.4). Правило «расширить → перенести → сузить»:
  - выпуск N добавляет колонку, таблицу или функцию;
  - выпуск N+1 переводит код на новое;
  - выпуск N+2 удаляет старое.
- Миграция, которая блокирует большую таблицу (`ALTER TABLE … SET NOT NULL` на миллионах строк, новый индекс без `CONCURRENTLY`), идёт только в окне обслуживания. Об этом предупреждает backend в контракте выпуска.
- Миграции запускает только `deploy.sh` (сервис `migrate`), до перезапуска сервера: сервер не опережает схему. `db:seed` и `db:reset` в проде не существуют.
- Журнал (`audit_log`) миграции не меняют: UPDATE и DELETE запрещены триггерами всем ролям (инвариант 2).

### 5.3. Инфраструктура: только в окне обслуживания

Окно — `MAINTENANCE_WINDOW` по `MAINTENANCE_TZ`, когда клубы закрыты (по умолчанию 06:00–10:00 по Москве, сверить с часами пилотного клуба).

```sh
deploy/prod/bin/infra-restart.sh mosquitto     # новый образ или настройки брокера в compose.yml
deploy/prod/bin/infra-restart.sh db            # сначала дамп; новый образ базы
deploy/prod/bin/infra-restart.sh caddy         # можно и днём: мосты ККТ и SSE переподключатся
```

Вне окна `infra-restart.sh` и `compose.sh` откажутся. Без перезапуска, в любое время:

- `caddy-reload.sh` — правка Caddyfile;
- `mqtt-reload.sh` — новый сертификат брокера или правка `mosquitto.conf`, через SIGHUP;
- клиенты и роли Dynamic Security — на ходу;
- `pg_hba.conf` — `select pg_reload_conf()`.

Обновление Docker, ядра и перезагрузка сервера — тоже только в окне. `live-restore` защищает от случайного перезапуска Docker, но не от перезагрузки.

### 5.4. Откат

План отката готовится до выпуска. Обычный откат кода:

```sh
deploy/prod/bin/rollback.sh            # на предыдущий выпуск из /var/lib/billiardum/releases.log
deploy/prod/bin/rollback.sh <sha>      # на указанный; образ billiardum-app:<sha> должен быть на сервере
```

Откат возвращает код, статику и `server` и `site` прежнего выпуска. Миграции не откатываются, поэтому важно правило §5.2.

Если новая схема всё-таки ломает старый код, нужно восстановить базу из дампа `predeploy/<время>-<sha>/`. Это потеря данных после выпуска, поэтому только с отдельного «да» Андрея (§7.5).

Образы прошлых выпусков не удаляются: широкий `docker prune` на сервере не запускается. Старые образы приложения удаляются по одному (`docker image rm billiardum-app:<sha>`), последние пять остаются.

### 5.5. Что нельзя делать в часы работы клубов

| Нельзя | Почему | Как правильно |
|---|---|---|
| Перезапускать, останавливать, пересоздавать `mosquitto` | обрывает связь всех контроллеров, новые игры не стартуют | SIGHUP (`mqtt-reload.sh`), Dynamic Security на ходу; перезапуск — в окне |
| Перезапускать `db` | без базы API не работает | в окне, `infra-restart.sh db` |
| `docker compose up -d` без имён сервисов или без `--no-deps` | Compose пересоздаст `db` и `mosquitto`, если их настройки разошлись с `.env` | `compose.sh up -d --no-deps <сервис>` (обёртка не даст) |
| `systemctl restart docker`, `apt upgrade docker-ce`, перезагрузка | перезапуск всех контейнеров | в окне |
| Менять `MQTT_ADMIN_PASSWORD` | вход брокера сверяет пароль только при старте | в окне, §8 |
| Прошивать контроллер на занятом столе | игра гостя | только свободный стол, по одному, с «да» Андрея |
| `docker system prune`, `docker volume prune` | удалит образы для отката, а при ошибке — тома | удалять по одному |

Авария, когда брокер или база уже лежат: `BL_EMERGENCY=1 deploy/prod/bin/infra-restart.sh mosquitto`. Скрипт спросит слово `АВАРИЯ`. Андрею — сразу сообщение, что и почему.

## 6. Мониторинг и тревоги

### 6.1. Что проверяется

`deploy/prod/monitor/monitor.sh` запускается раз в минуту (`billiardum-monitor.timer`).

| Проверка | Порог | Уровень |
|---|---|---|
| `https://{домен}/health` (сервер, база и брокер разом) | не отвечает | критично |
| TLS сайта | осталось меньше 14 дней (Caddy продлевает за 30) | внимание |
| TLS брокера `mqtt.{домен}:8883` по CA платформы | не принимает | критично |
| Срок сертификата брокера | меньше 90 дней | внимание |
| Контейнеры `db`, `mosquitto`, `server`, `site`, `caddy` | не `running healthy` | критично |
| Доля контроллеров онлайн (боевые клубы, `MONITOR_DEVICE_HOURS`) | без `state` дольше 10 мин, на связи меньше 90 % | внимание |
| Клуб целиком без связи | все контроллеры клуба дольше 10 мин | критично |
| Outbox: оплата → свет | `payment.*` не обработано дольше 2 мин | критично |
| Outbox: очередь | старшее событие ждёт дольше 5 мин | критично |
| Outbox: повторы | 5 и больше попыток | внимание |
| Очередь уведомлений | в очереди дольше 10 мин или 5 и больше сбоев за час | внимание |
| Очередь чеков (54‑ФЗ) | не пробит дольше 15 мин или ошибка за сутки | внимание |
| Мост ККТ | у боевого клуба без связи дольше 10 мин | внимание |
| Ошибки ЮKassa | тревоги денег за 15 мин (вебхук не пришёл, расхождение, возврат); 3 и больше `yookassa_error` в логе за 5 мин | внимание |
| Критичные тревоги клубов | открыты и не приняты дольше 30 мин | внимание |
| Сервер | `mqtt_disconnected`; 5 и больше `db_error`, `http_unhandled` за 5 мин | внимание |
| Диск (`/`, `/var/lib/docker`, `/var/lib/billiardum`) | 80 % и больше / 90 % и больше | внимание / критично |
| Память | свободно меньше 10 % | внимание |
| Архив WAL | `archive_command` падает / нет архива больше часа | критично / внимание |
| Бэкапы | нет ежедневного больше 26 ч / WAL не уходит 20 мин | критично / внимание |
| Службы systemd | любая `billiardum-*` упала (`OnFailure`) | критично |

Тревоги для владельцев клубов (офлайн стола через 120 с, свет в обход, чек не пробит 10 мин и другие) шлёт сам сервер. Монитор их не дублирует, а смотрит на платформу целиком и на то, что сервер сам сообщить не может.

Показатели базы — только агрегаты (`deploy/prod/monitor/checks.sql`): ни телефонов, ни имён гостей. Монитор читает их под `supabase_admin` внутри контейнера базы в транзакции `read only`: RLS не даёт рабочей роли `app_api` посчитать по всем клубам. Отдельная роль `bl_monitor` с узкой функцией — вопрос backend (§9).

### 6.2. Куда уходят тревоги

- **Telegram**: тот же бот платформы, только через `TELEGRAM_PROXY_URL`, в чаты `MONITOR_TELEGRAM_CHAT_IDS`. Это личный чат Андрея с ботом: его `chat_id` равен Telegram id Андрея. После §4.6 id можно узнать так:
  ```sh
  deploy/prod/bin/compose.sh exec -T db psql -U supabase_admin -h 127.0.0.1 -d postgres -Atc \
    "select u.telegram_user_id from bl.users u join bl.platform_members m on m.user_id = u.id where m.role = 'platform_admin' and m.active"
  ```
- **MAX** — основной канал продукта, но адаптер сервера пока заглушка: нет документации API MAX (`server/notify/max.mjs`). Переменная `MONITOR_MAX_USER_IDS` зарезервирована. До адаптера тревоги идут только в Telegram.
- **Журнал systemd** — всегда: `journalctl -t billiardum-alert`.

Монитор шлёт тревоги сам, а не через уведомления сервера: тревога должна дойти, когда сервер или база лежат. Внешних сервисов за рубежом нет. Сообщение повторяется раз в час, пока проблема не ушла (`MONITOR_REPEAT_MIN`), затем приходит «восстановлено».

Ручная проверка: `deploy/prod/monitor/monitor.sh --dry-run` печатает все показатели и ничего не отправляет.

### 6.3. Еженедельный отчёт пилота

`billiardum-pilot-report.timer` по понедельникам в 09:07 по Москве отправляет Андрею метрики PRODUCT §21 за 7 дней по каждому боевому клубу:

- доля игр без персонала;
- свет без записи в журнале;
- расхождения касс;
- медиана «скан → свет»;
- доля продлений из приложения.

Формулы — как в дашборде владельца (`server/dashboard/day.mjs`, M5.2), запрос — `deploy/prod/monitor/pilot-metrics.sql`. Если формулы дашборда меняются, файл сверяется с ними. Вручную: `deploy/prod/monitor/pilot-report.sh --print`.

### 6.4. Кто следит за самим сервером

Монитор работает на том же сервере. Если сервер выключен целиком, тревоги не будет. Закрывает это второй маленький сервер в РФ у другого провайдера (вопрос Андрею): на нём тот же репозиторий, файл настроек с доменом, ботом и прокси (без секретов базы), `ca.crt` и таймер с `monitor.sh --external-only`. Он проверяет домен, TLS и брокер снаружи и шлёт тревоги тем же ботом. Сервисы мониторинга за рубежом не подключаются.

## 7. Бэкапы

### 7.1. Что и куда

| Что | Когда | Куда (`BACKUP_RCLONE_REMOTE`) |
|---|---|---|
| Физический бэкап кластера (`pg_basebackup`, с WAL на время бэкапа) | ежедневно, 05:23 по Москве | `base/<время>/base.tar.gz.age` |
| Логический дамп базы (`pg_dump -Fc`) и роли (`pg_dumpall -g`) | там же | `base/<время>/postgres.dump.age`, `globals.sql.age` |
| `/etc/postgresql-custom` (supautils.conf и ключи образа) | там же | `base/<время>/postgresql-custom.tar.gz.age` |
| Клиенты и роли брокера (`dynamic-security.json`) | там же | `base/<время>/dynamic-security.json.age` |
| Архив WAL (`archive_timeout` 5 мин) | каждые 5 мин | `wal/<сегмент>.age` |
| Дамп перед выпуском | каждый `deploy.sh`, `infra-restart.sh db` | `predeploy/<время>-<sha>/` |
| Файл настроек и сертификаты брокера | при изменении | `secrets/*.age` — **только ключ Андрея** |

- Всё шифруется `age` на сервере до отправки. Открытого текста в хранилище нет.
- Бэкап базы и брокера открывают два ключа: Андрея (офлайн) и ключ проверки восстановления (`BACKUP_RESTORE_AGE_KEY` на сервере).
- Копию файла настроек открывает только ключ Андрея. `SECRETS_ENC_KEY` никогда не лежит рядом с дампом в виде, который откроет ключ сервера (№23).
- Хранилище — в РФ у другого провайдера, чем сервер. Ключ доступа сервера может только писать и читать, удалять не может. Срок хранения 35 дней задаёт правило жизненного цикла бакета. Если провайдер поддерживает блокировку версий (Object Lock), её стоит включить.
- В CI и разработку боевые дампы не попадают никогда (decisions №21).

### 7.2. RPO и RTO

| | Цель | Откуда |
|---|---|---|
| **RPO** (сколько данных можно потерять) | ≤ 10 мин при потере сервера; 0 — если диск цел | WAL закрывается не реже раза в 5 мин и уходит в хранилище каждые 5 мин |
| **RTO** на том же сервере (база испорчена) | ≤ 30 мин | скачать и расшифровать base и WAL, воспроизвести, запустить |
| **RTO** на новом сервере (сервер потерян) | ≤ 3 ч | заказ VPS в РФ, §4.1–4.4, восстановление базы и брокера, DNS (TTL 300) |

Пока сервер лежит, идущие оплаченные игры доигрываются на контроллерах (инвариант 3), а новые не стартуют (PRODUCT §20). Ежемесячная проверка измеряет фактические RPO и RTO и присылает их Андрею.

### 7.3. Проверка восстановления раз в месяц

`billiardum-restore-check.timer` запускается в первый вторник месяца в 06:17 по Москве, в окне обслуживания. Скрипт `deploy/prod/backup/restore-check.sh`:

1. Скачивает последний полный бэкап и WAL после него, расшифровывает ключом проверки.
2. Поднимает **отдельный** контейнер Postgres тем же образом без сети (`--network none`). Рабочую базу и брокер он не трогает.
3. Ждёт конца воспроизведения WAL.
4. Сверяет число миграций с рабочей базой, проверяет `bl.audit_verify` по каждому клубу (цепочки журнала целы), считает RPO (отставание от рабочей базы) и RTO (сколько заняло).
5. Шлёт отчёт Андрею, затем удаляет контейнер и папку.

Ошибка — критичная тревога. Вручную: `restore-check.sh --keep` оставит контейнер `bl-restore-check-<время>` для разбора.

Шаги 1–4 проверены на Postgres 16 с настоящими `pg_basebackup`, `age` и архивом WAL: строка, записанная после бэкапа, восстановилась из WAL, цепочка журнала цела.

### 7.4. Ключи бэкапов

| Ключ | Где | Если потерян |
|---|---|---|
| Ключ age Андрея (закрытый) | только офлайн у Андрея: менеджер паролей и бумажная копия | старые бэкапы открывает ключ проверки; копию файла настроек — никто. Создать новый ключ, обновить получателей |
| `BACKUP_RESTORE_AGE_KEY` | `/etc/billiardum/prod.env` | создать новый ключ (`age-keygen`), заменить открытый в `BACKUP_AGE_RECIPIENTS`; старые бэкапы открывает ключ Андрея |
| `SECRETS_ENC_KEY` | `prod.env` и офлайн у Андрея (из `secrets/prod.env.*.age`) | ключи контроллеров и магазинов клубов не расшифровать: перепривязка всех контроллеров, клубы вводят ключи ЮKassa заново, PIN персонала сбрасываются (их соль выводится из этого ключа) |
| `ca.key` CA платформы | офлайн у Андрея | новый сертификат брокера не выпустить: в течение 5 лет нужна прошивка с новым CA |

### 7.5. Восстановление

Требует «да» Андрея: это откат данных на момент бэкапа. Сначала сохраняется копия текущего состояния.

**База испорчена, сервер цел** (в окне обслуживания или аварийно):

```sh
cd /opt/billiardum
deploy/prod/bin/compose.sh stop server site
BL_EMERGENCY=1 deploy/prod/bin/compose.sh stop db          # вне окна — только авария
# копия испорченного тома — на случай, если понадобится
docker run --rm --network none -v billiardum-prod_db-data:/from -v billiardum-prod_db-data-broken-$(date +%Y%m%d):/to \
  supabase/postgres:15.8.1.085@sha256:af083ef64d0408c8f098ee6f5c364a59b26f36fbc0f3a334a62c5c1d57362e9b sh -c 'cp -a /from/. /to/'
```

Дальше — те же шаги, что в `restore-check.sh`, но в рабочий том:

1. Скачать и расшифровать `base.tar.gz.age` нужной даты (ключ Андрея или `BACKUP_RESTORE_AGE_KEY`). Очистить том `billiardum-prod_db-data` и распаковать в него с `tar --no-same-owner`, владелец — postgres образа.
2. Скачать и расшифровать WAL в `/var/lib/billiardum/wal-archive/restore/`. Эту папку `wal-push.sh` не трогает, в контейнере она видна как `/wal-archive/restore`.
3. В `postgresql.auto.conf` тома дописать `restore_command = 'cp /wal-archive/restore/%f %p'`. Для отката на момент перед ошибкой — ещё `recovery_target_time = '…+00'`. Создать `recovery.signal`.
4. `BL_EMERGENCY=1 deploy/prod/bin/compose.sh up -d --no-deps --wait db`. Postgres воспроизведёт WAL и перейдёт на новую линию времени.
5. `compose.sh exec -T -u postgres db sh -s < deploy/postgres/reserved-roles.sh`, затем `compose.sh up -d --no-deps --wait server site`.
6. Контроллеры сами сверят `seq`: сервер поднимет счётчик по `state` и запишет `device.seq_sync` в журнал (протокол §6).
7. Платежи за потерянный интервал сверить в личном кабинете ЮKassa клуба. Вебхуки, которые ЮKassa повторяет, сервер перепроверяет запросом. Чеки ККТ сверить по отчёту ККТ.

**Сервер потерян**:

1. Новый сервер в РФ, §4.1–4.2.
2. Андрей расшифровывает своим ключом последние `secrets/prod.env.*.age` и `secrets/mqtt-certs.*.tar.age` и передаёт их на сервер в `/etc/billiardum/`.
3. До первого старта брокера положить `dynamic-security.json` из бэкапа в том `billiardum-prod_mosquitto-data`. Тогда контроллеры войдут со своими паролями, и перепривязка не нужна.
4. Базу восстановить, как выше, в новый том. `/etc/postgresql-custom` — из `postgresql-custom.tar.gz.age`.
5. `deploy.sh <выпуск>`, затем `caddy`, затем DNS обоих имён на новый IP. Контроллеры найдут брокер по имени `mqtt.{домен}`.

## 8. Ротация секретов

Значения не показываются никому, в том числе в чатах агентов. После любой ротации — `preflight.sh`, а `pg-backup.sh` при ближайшем запуске сам положит новую копию настроек в `secrets/`.

| Секрет | Как сменить | Простой |
|---|---|---|
| `POSTGRES_PASSWORD` (supabase_admin) | `compose.sh exec -T db psql -U supabase_admin -h 127.0.0.1 -d postgres -c "\password supabase_admin"` с новым значением, затем то же значение в `prod.env`. Переменная контейнера `db` нужна только при создании тома, пересоздавать `db` не надо | нет |
| `DB_APP_PASSWORD` (app_api) | новое значение в `prod.env` → `compose.sh run --rm --no-deps migrate` (раннер ставит пароль) → сразу `compose.sh up -d --no-deps --wait server` | секунды |
| `MQTT_SERVER_PASSWORD` | `prod.env` → `compose.sh run --rm tools node deploy/prod/bin/mqtt-server-client.mjs` (без `--if-missing`). Пароль меняется на ходу, но `modifyClient` отключает работающий сервер, а со старым паролем он не войдёт. Поэтому сразу `compose.sh up -d --no-deps --wait server` (проверено на Mosquitto 2.0) | секунды |
| `MQTT_ADMIN_PASSWORD` | **только в окне**: `prod.env` → `infra-restart.sh mosquitto` (вход брокера ставит новый пароль) → `compose.sh up -d --no-deps --wait server` | минута в окне |
| Сертификат брокера | `mqtt-certs.sh issue` тем же CA (на ноутбуке Андрея) → файлы в `/etc/billiardum/mqtt/` → `mqtt-reload.sh`. Проверено: после SIGHUP брокер отдаёт новый сертификат, клиенты не отключаются | нет |
| CA платформы | только вместе с новой прошивкой (новый `kMqttCaPem`) по одному столу, по «да» Андрея; на время перехода брокер с сертификатом нового CA, а прошивка доверяет обоим CA (вопрос firmware) | план отдельно |
| `SECRETS_ENC_KEY` | простой заменой нельзя: им зашифрованы `device_key` и ключи ЮKassa в базе, из него выводится соль PIN. Нужен скрипт перешифровки (вопрос backend, §9). При утечке до появления скрипта: новый ключ, перепривязка контроллеров, клубы вводят ключи ЮKassa заново, PIN задаются заново | план отдельно |
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/revoke` → `prod.env` → `compose.sh up -d --no-deps --wait server` → `telegram-webhook.mjs` | секунды для входа через Telegram |
| `TELEGRAM_WEBHOOK_SECRET` | `prod.env` → пересоздать `server` → `telegram-webhook.mjs` | секунды |
| `VAPID_*` | только парой (`gen-env.sh` на пустом файле, перенести две строки) → пересоздать `server`; подписки Web Push у гостей перестанут работать до повторной подписки | нет, но гости теряют push |
| `PLATFORM_YOOKASSA_SECRET` | новый ключ в личном кабинете ЮKassa платформы → `prod.env` → пересоздать `server` → старый ключ отозвать | секунды |
| Ключи ЮKassa клубов | владелец меняет в программе клуба (ручное действие с причиной и тревогой, №154) | нет |
| Ключи контроллеров | перепривязка контроллера (протокол §7) | стол на минуты, только свободный |
| Токен моста ККТ | владелец отзывает мост и выдаёт новый токен (README «Мост ККТ») | чеки ждут в очереди |
| Ключи хранилища бэкапов | новый ключ у провайдера → `prod.env` → проверить `systemctl start billiardum-wal-push` → старый отозвать | нет |
| Ключи age | §7.4 | нет |

## 9. Открытые вопросы и ограничения

- **Роль `bl_monitor` для монитора** (backend). Сейчас монитор и отчёт читают агрегаты под `supabase_admin` внутри контейнера базы. Лучше — роль без входа извне с одной функцией `SECURITY DEFINER`, которая возвращает только числа.
- **Перешифровка `SECRETS_ENC_KEY`** (backend): скрипта нет, ротация ключа невозможна без перепривязки (§8).
- **MAX-бот** (backend): адаптер — заглушка, тревоги Андрею идут только в Telegram через прокси.
- **Второй сервер-сторож в РФ** (Андрей): без него полное падение сервера не даёт тревоги (§6.4).
- **Два CA в прошивке** (firmware): чтобы CA платформы можно было сменить без «кирпичей».
- **Адреса ЮKassa для вебхуков** — сверить с документацией ЮKassa перед пилотом (`YOOKASSA_WEBHOOK_IPS`).
- **Сборка на сервере** тянет пакеты npm и образы Docker Hub из-за рубежа: код и зависимости, без данных гостей. Альтернатива — реестр образов в РФ (Yandex Container Registry), когда выпусков станет больше.
