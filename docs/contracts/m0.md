# Контракты M0 «Фундамент»

Автор: оркестратор. Отклонение — только через оркестратора. Если контракт мешает сделать правильно, исполнитель пишет замечание в отчёте, а не обходит контракт молча.

Цель M0 (ROADMAP): `npm run dev` поднимает всё с нуля; симулятор показывает 8 столов онлайн в логе сервера; UPDATE и DELETE в `audit_log` падают для любой роли; CI зелёный. Дополнительно (оркестратор): TRUNCATE журнала падает; клуб A не видит данные клуба B; устройство не пишет в чужие топики и в свой `cmd`.

## 1. Пакеты и команды

npm workspaces. Корневой `package.json` ведёт devops.

| Пакет | Папка | Владелец | Зависимости |
|---|---|---|---|
| `@billiardum/shared` | `shared/` | frontend | нет |
| `@billiardum/db` | `supabase/` | backend | `pg` |
| `@billiardum/server` | `server/` | backend | `pg`, `mqtt` |
| `@billiardum/device-sim` | `tools/device-sim/` | firmware | `mqtt` |

Все пакеты: `"type": "module"`, `"engines": {"node": ">=22"}`, тесты `node --test`, скрипт `test` в каждом пакете.

Команды корня (devops связывает их с пакетами):

| Команда | Что делает | Реализует |
|---|---|---|
| `npm run dev` | поднимает всё с нуля и показывает логи сервера и симулятора | devops |
| `npm run down` | останавливает окружение; `npm run down -- --volumes` стирает данные | devops |
| `npm test` | юнит-тесты всех пакетов (без базы и брокера) | devops (связка) |
| `npm run test:db` | тесты базы на поднятом Postgres | backend (`supabase/`) |
| `npm run lint` | ESLint по всему репозиторию | devops |
| `npm run ci` | то же, что CI, локально: lint, test, миграции на чистой базе, test:db | devops |
| `npm run db:migrate` | применяет `supabase/migrations/*.sql` по порядку, учёт в `schema_migrations`; задаёт пароль `app_api` из `DB_APP_PASSWORD` | backend |
| `npm run db:seed` | применяет `supabase/seed.sql` (только разработка) | backend |
| `npm run db:reset` | стирает схему, migrate, seed (только разработка, отказ при `NODE_ENV=production`) | backend |
| `npm run provision:dev` | создаёт в Dynamic Security клиента `bl-server` и 8 устройств сида, генерирует `device_key`, пишет их в базу зашифрованными и в `deploy/dev/devices.json`; повторный запуск безопасен | backend (`server/bin/`) |
| `npm run sim` | запускает симулятор с хоста по `deploy/dev/devices.json` | firmware |

DB-инструменты backend кладёт в `supabase/bin/`, провижининг — в `server/bin/`: так зависимости остаются внутри пакетов.

## 2. Docker Compose (`deploy/dev/compose.yml`)

Имя проекта Compose: `billiardum`.

| Сервис | Образ | Порт на хосте | Назначение |
|---|---|---|---|
| `db` | `supabase/postgres:15.8.1.085` | 54322 → 5432 | Postgres с RLS |
| `mosquitto` | `eclipse-mosquitto:2` | 8883 → 8883 | MQTT по TLS, Dynamic Security, анонимный вход запрещён |
| `server` | `node:22-alpine` | 3000 → 3000 | `node server/index.mjs` |
| `device-sim` | `node:22-alpine` | — | `node tools/device-sim/index.mjs` |
| `caddy` | `caddy:2-alpine` | 8443 → 443 | `https://localhost:8443` → `server:3000`, `tls internal` |

Миграции, сид и провижининг выполняются до старта `server` и `device-sim` (способ выбирает devops: шаг в `scripts/dev.mjs` или одноразовый сервис). Старт `npm run dev` на чистой машине требует только Docker и Node 22.

Mosquitto: слушатель 8883 только TLS, `allow_anonymous false`, плагин Dynamic Security с файлом в томе данных. Администратор Dynamic Security `bl-admin` создаётся при первом старте брокера из `MQTT_ADMIN_PASSWORD`. Порт 1883 не открывается.

| `MQTT_CA_FILE` | `deploy/dev/certs/ca.crt` | `server`, `device-sim`, провижининг |
| `MQTT_ADMIN_USER`, `MQTT_ADMIN_PASSWORD` | `bl-admin`, — | `mosquitto` (создание), провижининг, `server` |

## 5. База (backend)

Таблицы M0: `users` (минимум: `id`, `phone`, `created_at`), `clubs`, `club_members`, `resources`, `devices`, `tariff_rules`, `audit_log`, `schema_migrations`.

**Своя схема `bl`, а не `public`.** В образе `supabase/postgres` роли `postgres`, `service_role` и `supabase_read_only_user` имеют `BYPASSRLS`, а `authenticator` может переключиться в `anon`, `authenticated`, `service_role`; кроме того, Supabase раздаёт этим ролям права на новые таблицы в `public` по умолчанию. Поэтому все наши объекты — в схеме `bl`, на схему и таблицы нет никаких прав у ролей Supabase (`anon`, `authenticated`, `service_role`, `authenticator`, `postgres`, `supabase_read_only_user` и остальных); права есть только у `app_api` и у владельца. Проверено оркестратором на образе 15.8.1.085: суперпользователь — `supabase_admin`, `postgres` суперпользователем не является.

- `clubs`: `id`, `name`, `city`, `timezone` (IANA), `settings jsonb`, `created_at`.
- `resources`: `id`, `club_id`, `type` (`billiard_pyramid`, `billiard_pool`, `billiard_snooker`), `number`, `title`, `plan_x`, `plan_y`, `plan_rotation`, `active`.
- `devices`: `id` (= `device_id`), `club_id`, `resource_id` (уникально), `serial`, `device_key_enc`, `mqtt_username`, `last_seq bigint not null default 0`, `fw`, `caps text[]`, `last_seen_at`, `created_at`.
- `tariff_rules`: `club_id`, `resource_type` или `resource_id`, `days smallint[]` (ISO 1–7), `start_local time`, `end_local time`, `price_per_hour` (копейки, `bigint`), `step_minutes` (1), `min_minutes` (30), `priority`. Семантика праздников и ночных интервалов — M1.
- `club_members`: `club_id`, `user_id`, `role` (`owner`, `manager`, `reception`, `installer`), `pin_hash`, `active`.
- Все таблицы с `club_id`: `ENABLE` и `FORCE ROW LEVEL SECURITY`; владелец таблиц — роль без входа; `app_api` без `BYPASSRLS` и не владеет таблицами (decisions №12).
- Контекст запроса: в каждой транзакции `server` вызывает `set_config('app.club_id', …, true)`, `set_config('app.user_id', …, true)`, `set_config('app.actor_type', 'user'|'system'|'device'|'support', true)`. Политики отсекают всё вне `app.club_id`. Чтение через клубы (найти клуб устройства по `device_id`) — только узкие функции `SECURITY DEFINER` с фиксированным набором полей, список в `supabase/README.md`.

### `audit_log`

Поля: `id`, `club_id` (NULL — цепочка платформы), `seq` (позиция в цепочке клуба), `created_at`, `actor_type`, `actor_id`, `action`, `object_type`, `object_id`, `reason`, `data jsonb`, `prev_hash`, `hash` (hex sha256).

- Приложение делает обычный `INSERT` без `seq`, `created_at`, `prev_hash`, `hash`: их задаёт триггер `BEFORE INSERT` и перезаписывает присланные (decisions №13). Первая запись цепочки: `prev_hash` = 64 нуля.
- Формула хеша детерминирована, включает все поля и описана в `supabase/README.md`.
- Функция `audit_verify(club uuid)` возвращает `ok` и номер первой испорченной записи.
- `UPDATE`, `DELETE`, `TRUNCATE` запрещены триггерами для всех ролей. Таблица принадлежит отдельной роли без входа, которую никому не выдают.

### Сид (`supabase/seed.sql`, decisions №17)

- Клуб «Тестовый клуб», Екатеринбург, `Asia/Yekaterinburg`.
- 8 столов: 1–5 `billiard_pyramid`, 6–8 `billiard_pool`, координаты на плане зала.
- Тарифы из PRODUCT §9 для обоих типов столов.
- 8 устройств с фиксированными UUID, по одному на стол; ключи задаёт `provision:dev`.
- Владелец: пользователь с телефоном `+70000000001` (синтетический).

### Тесты базы (`npm run test:db`)

- `UPDATE`, `DELETE`, `TRUNCATE` в `audit_log` падают для каждой роли, которая есть в базе и может войти или в которую можно переключиться: суперпользователь, роль миграций, `app_api`, `anon`, `authenticated`, `service_role`, `authenticator`.
- 50 параллельных вставок в один клуб: `seq` без пропусков, `audit_verify` — `ok`.
- Подмена записи суперпользователем в обход триггеров (`session_replication_role = replica`) — `audit_verify` показывает номер испорченной записи.
- Два клуба: с контекстом клуба A `app_api` не видит строк клуба B ни в одной таблице и не может вставить строку с `club_id` клуба B.
- Без контекста клуба `app_api` не видит ни одной строки с `club_id`.
- Роли Supabase с `BYPASSRLS` и роли, доступные `authenticator`, не могут прочитать ни одной таблицы схемы `bl`.

## 6. Сервер (backend)

- `server/index.mjs`: HTTP на `PORT`, `GET /health` → `200 {"ok":true,"db":true,"mqtt":true}`, при недоступности зависимости `503` с тем же видом.
- `server/mqtt.mjs`: подключается как `bl-server`, подписан на `bl/v1/+/+/state`, `status`, `event`, `ack`. Устройство и клуб определяет по `device_id` из базы, а не по топику.
- Устройство онлайн: `status = online` и получен `state`. Офлайн: `status = offline` или нет `state` 150 с.
- Когда устройство стало онлайн, сервер отправляет ему `ping` по протоколу v1: `seq` и запись в журнал (`action = 'device.cmd'`, `object_type = 'device'`, `data = {cmd_id, seq, type}`) в одной транзакции, публикация после коммита, повтор без `ack` по протоколу §6.
- Лог — строки JSON в stdout, без персональных данных. Обязательные:
  - `{"t":"…","level":"info","msg":"devices_online","online":8,"total":8}` — при каждом изменении и раз в 60 с; `total` — число устройств в базе;
  - `{"t":"…","level":"info","msg":"cmd_ack","device_id":"…","type":"ping","seq":N,"ok":true}`.
- Подпись команд — общий модуль сервера, тест на все векторы `docs/protocol-vectors.json`.

## 7. Симулятор (firmware)

- `tools/device-sim/index.mjs`: читает `SIM_DEVICES_FILE`, поднимает по столу на устройство, подключается по TLS с CA из файла, клиент и логин — `device_id`.
- Last Will `offline` (retained) в `status`, после подключения `online` (retained), `state` при изменении и раз в 60 с, событие `boot` при старте (`boot` и `n` по протоколу).
- Принимает команды: разбор и подпись по протоколу §3.1, `seq` и повтор по §3.2, `ack` по §4. В M0 из типов исполняются `ping` и `identify`, остальные — `unknown_type` до M1, но формат, подпись и `seq` проверяются для всех.
- NVS — в памяти процесса; интерфейс хранилища отделён, чтобы в M1 добавить перезагрузки.
- Лог — строки JSON: `{"t":"…","level":"info","msg":"sim_state","device_id":"…","table":4,"mode":"free","relay":false,"led":"green_dim"}` при изменении.
- Тест на все векторы `docs/protocol-vectors.json` и на таблицу повторов §3.2.

## 8. Общий пакет `shared/` (frontend, задача 6)

- `shared/tokens.css`: токены DESIGN.md §2 — светлая тема по умолчанию, тёмная по `prefers-color-scheme` и вручную через `data-theme="dark"`/`"light"` на `<html>`, токены зала `--hall-*` одинаковы в обеих темах.
- `shared/fonts/`: Dela Gothic One, Geologica (300–700), JetBrains Mono (500, 700) в WOFF2, подмножества кириллица и латиница, `font-display: swap`, файл `shared/fonts.css`, лицензии OFL рядом. Источник — npm-пакеты Fontsource, файлы копируются в репозиторий.
- `shared/format.mjs`: `plural(n, [one, few, many])`, `formatMoney(kopecks)` → «1 490 ₽», `formatTime(date, timeZone)` → «21:30», `formatDate(date, timeZone)` → «21 октября», `formatDuration(ms)` → «1:05:00». Тесты: 0, 1, 2, 5, 11, 12, 14, 21, 22, 25, 101, 111, 1 000 000 для `plural`; копейки, ноль и миллионы для денег; часовой пояс `Asia/Yekaterinburg` и переход через полночь для времени.
- `shared/styleguide.html`: страница токенов, шрифтов и образца плана зала (8 столов, занятые освещены) в обеих темах. Без внешних ресурсов.
- `shared/icons/` в M0 не нужен.

## 10. Порты для параллельной работы агентов в одной машине

Чтобы не мешать друг другу до сборки общего окружения:
- devops — основной стек на портах из раздела 2, проект Compose `billiardum`;
- backend — свой Postgres для тестов: контейнер `bl-backend-pg`, порт 55432;
- firmware — свой брокер для тестов симулятора: контейнер `bl-sim-mqtt`, порт 18883;
- frontend — без контейнеров.

Демон Docker общий, его не останавливать. Чужие контейнеры не трогать.
