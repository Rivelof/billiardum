# Контракты M2 «Касса, бар, смены»

Автор: оркестратор. **Черновик**, пишется во время приёмки M1; фиксируется после закрытия M1. Отклонение — только через оркестратора.

Цель M2 (ROADMAP): сценарии T13–T17; сверка за смену сходится до копейки на тестовом дне из 50 продаж разными способами.

Ограничения среды: настоящей ККТ нет, документация АТОЛ из среды не открывается. Мост ККТ проверяется на эмуляторе веб-сервера драйвера АТОЛ (`tools/kkt-bridge/emu/`, порт по умолчанию 16732 как у настоящего веб-сервера). Поля заданий АТОЛ, в которых нет уверенности, перечисляются для сверки со Swagger драйвера 10.x.

---

## 1. Решения M2 (записываются в decisions.md)

1. **Алкоголь скрывает сервер, а не интерфейс:** у товара флаг `is_alcohol`; QR-меню и заказ со стола отдают и принимают только товары без него, пока в настройках платформы не включено `qr_alcohol_allowed` (включает только Андрей после заключения юриста). Ресепшн продаёт алкоголь как обычно.
2. **Мост ККТ — исходящее WebSocket-соединение** от `tools/kkt-bridge/` к серверу (`wss://{PUBLIC_HOST}/api/kkt/ws`), токен моста на клуб и ПК (в базе — хеш). Сервер шлёт задания на чек, мост отвечает номером ФД, ФП и временем. Наружу на ПК ничего не открыто.
3. **Задание на чек идемпотентно** по `receipt_id` (UUID задания АТОЛ = `receipt_id`): повтор после обрыва не пробьёт второй чек.
4. **Счёт стола:** заказ бара «в счёт стола» привязан к сессии; при закрытии сессии счёт остаётся открытым у гостя и на ресепшене до оплаты. Свет от открытого счёта не зависит.
5. **Остатки — движения склада:** продажа, приход, списание, ревизия — строки `stock_movements`; остаток — сумма движений. Себестоимость — средняя по приходам.
6. **Смена:** наличные в кассе = размен + наличные продажи − наличные возвраты. Закрытие без ввода факта невозможно; расхождение ≠ 0 — тревога владельцу сразу.
7. **Скидки:** лимит скидки ресепшена — настройка клуба (по умолчанию 10 %); выше — только управляющий с причиной, тревога владельцу (инвариант 8). Удаление позиции из оплаченного чека — только возвратом с причиной.

## 3. Модель данных

- `product_categories`, `products` (`price_kopecks`, `is_alcohol`, `vat_code`, `payment_subject`, `stop_list`, `photo`, `unit`), `modifier_groups`, `modifiers` (`price_delta_kopecks`, `stock_factor`).
- `orders` (`source`: `qr`, `pos`; `status`: `new`, `preparing`, `ready`, `served`, `canceled`; `session_id` для «в счёт стола»; `payment_id`), `order_items` (снимок цены и модификаторов).
- `stock_movements` (`kind`: `sale`, `arrival`, `writeoff`, `audit`, `return`; `qty`, `cost_kopecks`), `stock_audits`.
- `shifts` (`opened_by`, `float_kopecks`, `expected_cash_kopecks`, `actual_cash_kopecks`, `discrepancy_kopecks`, `closed_at`).
- `receipts` (M1) дополняются: `kkt_job` (задание АТОЛ), `fd`, `fp`, `fn`, `printed_at`, `attempts`, `error`.
- `kkt_bridges` (клуб, имя ПК, хеш токена, последний онлайн, модель ККТ).

## 4. API (черновик)

| Метод и путь | Кто | Назначение |
|---|---|---|
| `GET /api/clubs/{club}/menu` | гость (без алкоголя), персонал | меню с остатками и стоп-листом |
| `POST /api/orders` | гость | заказ со стола: `{session_id, items, pay: "online"\|"tab"}` |
| `GET /api/orders/{id}` | гость, персонал | статус заказа |
| `POST /api/pos/sales` | ресепшн и выше, `Idempotency-Key` | продажа: корзина (товары, заявка стола, пакет часов, депозит), скидка, оплата `cash`\|`card_terminal`\|`sbp` |
| `POST /api/pos/sales/{id}/refund` | управляющий и выше | возврат с причиной |
| `GET /api/clubs/{club}/bar/queue` + SSE `bar` | бар, ресепшн | очередь заказов |
| `POST /api/orders/{id}/status` | бар, ресепшн | `preparing` → `ready` → `served` |
| `POST /api/sessions/{id}/tab/pay` | гость, ресепшн | оплата счёта стола |
| `POST /api/clubs/{club}/shifts` | ресепшн | открыть смену с разменом |
| `POST /api/shifts/{id}/close` | ресепшн | закрыть: факт наличных → расхождение, отчёт владельцу |
| `GET /api/shifts/{id}/report` | владелец, управляющий | отчёт смены и сверка |
| `POST /api/stock/arrivals`, `/writeoffs`, `/audits` | управляющий | склад |
| `GET /api/kkt/ws` (WebSocket) | мост ККТ | задания на чек |
| `POST /api/clubs/{club}/kkt/bridges` | владелец | регистрация моста, выдача токена |

Чек в задании АТОЛ: позиции с ценой, количеством, `vat`, `paymentObject`, `paymentMethod`; оплаты `cash`/`electronically`; кассир — имя сотрудника смены; система налогообложения клуба.

## 5. Сценарии и приёмка

T13 продажа бара наличными со сдачей → чек ККТ, остаток уменьшился. T14 ККТ выключена во время продажи → продажа сохранена, `receipt_pending`, предупреждение, чек пробит после включения. T15 заказ со стола «в счёт стола» → заказ на экране бара, счёт закрывается при уходе. T16 закрытие смены с недостачей 500 ₽ → расхождение в отчёте, уведомление владельцу. T17 повторный вебхук ЮKassa → одна оплата, одна сессия (есть с M1, повторить на кассе). Сверка: 50 продаж разными способами — сумма чеков ККТ = продажи, онлайн = ЮKassa (эмулятор), до копейки.
