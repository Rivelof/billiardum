# Протокол контроллера стола v1

Статус: **v1, утверждён 21.10.2026** оркестратором, firmware и backend на этапе M0 (decisions №14, №30–33, №37). Собран из v0 с правками по ревью обеих сторон.
Любое изменение после утверждения — только через оркестратора и с согласия firmware и backend. Несовместимое изменение повышает версию в топике и в поле `v`.

Тестовые векторы подписи: `docs/protocol-vectors.json`. Прошивка, симулятор и сервер обязаны их проходить.

## 1. Железо одного стола

| Узел | Назначение | Обязателен | `caps` |
|---|---|---|---|
| ESP32 (Wi-Fi) | логика, связь, таймер | да | — |
| Реле или твердотельное реле на линию лампы | свет | да | `relay` |
| Индикатор (RGB-светодиод, например WS2812) | состояние стола гостю | да | `led` |
| Пищалка | сигнал конца игры | да | `buzzer` |
| Датчик тока на линии лампы (бесконтактный трансформатор тока или модуль на эффекте Холла) | свет в обход системы, неисправность лампы | да | `current` |
| Блок питания 220 → 5 В, корпус, предохранитель | питание и безопасность | да | — |
| Выход ШИМ или 0–10 В на диммер | приглушение в льготу | если лампа диммируемая | `dimmer` |

Два пути для пилота (PRODUCT §22.1, решает Андрей):
- **A. Своя плата.** Полный контроль, датчик тока и индикатор сразу. Дольше до первого стола.
- **B. Готовое Wi-Fi-реле на ESP32 с нашей прошивкой.** Быстрее к пилоту. Индикатор, пищалку и датчик тока придётся добавить или отложить.

Прошивка пишется с прослойкой драйверов (`relay`, `led`, `buzzer`, `current`, `dimmer`), чтобы смена платы не меняла логику и протокол. Контроллер сообщает, что у него есть, в `caps` (раздел 4). Если `current` нет, сервер показывает владельцу, что защита от света в обход на этом столе выключена.

Флеш ESP32 — не меньше 4 МБ: для отката прошивки (раздел 8) нужны два раздела приложения.

Монтаж в линию 220 В делает только электрик.

## 2. Связь

- MQTT 3.1.1 по TLS (порт 8883), брокер Mosquitto на сервере платформы.
- Сертификат CA сервера закреплён в прошивке (CA pinning).
- У каждого контроллера свой логин (`device_id`, он же MQTT client id) и пароль. Пароль MQTT и ключ подписи `device_key` — разные секреты.
- Доступ — плагин Mosquitto Dynamic Security (decisions №15). При привязке сервер создаёт устройству клиента и роль с точными топиками `bl/v1/{club_id}/{device_id}/`: чтение `cmd`; запись `ack`, `state`, `event`, `status`. Ничего другого устройство не читает и не пишет. Анонимный вход запрещён.
- Сервер подключается отдельной учётной записью с доступом ко всем топикам `bl/v1/#` и к управлению Dynamic Security.
- Сервер не доверяет `club_id` из топика: устройство и его клуб определяются по таблице `devices`. Расхождение — событие в журнал и тревога.
- `keepalive` 30 с. Last Will: в `status` — `offline`, retained. После подключения контроллер подписывается на `cmd`, затем публикует `online` (retained) и `state`.
- `clean session = true` у контроллеров и сервера: брокер не копит команды для офлайн-устройства. Устаревшая команда пришла бы с опозданием, а остаток считается от момента получения — гость получил бы лишнее время.
- Предельный размер: `cmd` — 2048 байт, `state` и `event` — 4096 байт. Больше — `bad_format` (контроллер) или отброс с записью в лог (сервер).
- TLS не ниже 1.2, сертификат брокера ECDSA P-256 (ECDHE-ECDSA есть в mbedTLS). Без SNTP срок сертификата контроллер не проверяет, доверие держится на закреплённом CA.
- В прошивке — клиент esp-mqtt из ESP-IDF: QoS 1, retained Last Will, mbedTLS. PubSubClient не подходит: не публикует с QoS 1.

### Топики

Префикс: `bl/v1/{club_id}/{device_id}/`

| Топик | Направление | QoS | Retained | Содержимое |
|---|---|---|---|---|
| `cmd` | сервер → контроллер | 1 | нет | команды |
| `ack` | контроллер → сервер | 1 | нет | подтверждение команды |
| `state` | контроллер → сервер | 1 | да | текущее состояние |
| `event` | контроллер → сервер | 1 | нет | события (тревоги, перезагрузка) |
| `status` | контроллер → сервер | 1 | да | строка `online` или `offline` (Last Will) |

## 3. Команды (`cmd`)

Общий вид:

```json
{
  "v": 1,
  "id": "0192f3c1-6d1a-7c3e-9b2a-1f0e5d4c3b2a",
  "seq": 1842,
  "type": "session.start",
  "issued_at": 1792598400,
  "body": { },
  "sig": "base64(HMAC-SHA256(device_key, canonical_json_without_sig))"
}
```

Обязательные поля и форматы:

| Поле | Формат |
|---|---|
| `v` | целое `1` |
| `id` | UUID в нижнем регистре (`8-4-4-4-12` шестнадцатеричных цифр) |
| `seq` | целое ≥ 1, строго растёт для каждого устройства; сервер выделяет его атомарно в базе (раздел 6) |
| `type` | непустая строка из таблицы 3.3 |
| `issued_at` | целое ≥ 0, секунды Unix по часам сервера, только для журнала: часам контроллера не доверяем |
| `body` | объект; неизвестные поля тела игнорируются |
| `sig` | ровно 44 символа: base64 от 32 байт с одним `=` в конце |

### 3.1. Подпись

- `device_key` — 32 случайных байта, выдаётся при привязке, хранится в базе зашифрованным (decisions №23), в протоколе передаётся в base64.
- `sig` = base64 (стандартный алфавит, с `=`) от HMAC-SHA256(`device_key`, байты UTF-8 канонической строки).
- Сообщение — строгий JSON по RFC 8259. Дополнительно запрещены (`bad_format`): обратная косая черта где угодно в сообщении (любое экранирование, даже раскрывающееся в допустимый символ), повторяющиеся ключи, `-0`.
- Каноническая строка — сообщение без поля `sig` верхнего уровня, записанное так:
  - ключи объектов по возрастанию байтов на всех уровнях вложенности;
  - без пробелов и переводов строк: разделители `,` и `:`;
  - числа — только целые от −(2^53−1) до 2^53−1, запись без знака `+`, ведущих нулей и экспоненты. Число, записанное с точкой или экспонентой (`1.0`, `9e5`), — `bad_format`, даже если значение целое. В Node это проверяется по исходному тексту числа (третий аргумент reviver в `JSON.parse`, `context.source`), в ArduinoJson — тем, что значение разобрано как целое;
  - строки — только печатный ASCII (0x20–0x7E) без `"` и `\`, в двойных кавычках, без экранирования (decisions №31);
  - `true`, `false`, `null` как есть; массивы сохраняют порядок.
- Поле с именем `sig` где-либо кроме верхнего уровня запрещено.
- Сравнение подписи — за постоянное время.
- Проверка и исполнение идут по одному и тому же разобранному объекту.

Порядок проверки в контроллере:
1. Сообщение длиннее 2048 байт, JSON не строгий, нарушено правило канонизации, обязательное поле отсутствует или не того формата → `bad_format`.
2. `sig` отсутствует, не 44 символа base64 или не совпадает → `bad_sig`, событие и тревога.
3. `seq` и `id` (раздел 3.2).
4. Тип и тело: `unknown_type`; тело не подходит типу (нет поля, не тот тип значения, значение вне диапазона) → `bad_body`; `wrong_session`, `busy_ota`, `hw_fault`. С шага 4 `seq` считается принятым: ответ сохраняется и повторяется при точном повторе.

### 3.2. Повтор и защита от повтора

Контроллер хранит в NVS последний принятый `seq`, `id` этой команды и её `ack` (`ok`, `error`, `state_seq`) одним блоком. Порядок: исполнить → записать блок в NVS → опубликовать `ack`.

| Пришло | Ответ |
|---|---|
| `seq` больше сохранённого | исполнить, сохранить `seq`, `id`, `ack` |
| `seq` равен сохранённому и `id` тот же | **не исполнять**, отправить сохранённый `ack` (штатный повтор сервера, раздел 6) |
| `seq` равен сохранённому, `id` другой | `replayed_seq`, событие |
| `seq` меньше сохранённого | `replayed_seq`, событие |

При привязке (раздел 7) контроллер обнуляет `seq`, `id` и `ack`, сервер — `devices.last_seq`.

### 3.3. Типы команд

| `type` | `body` | Что делает контроллер |
|---|---|---|
| `session.start` | `session_id` (UUID), `remaining_ms` (1…86 400 000), `warn_ms` (ровно 2 целых по убыванию, каждое 1…3 600 000; по умолчанию `[300000, 60000]`), `grace_ms` (0…600 000, по умолчанию `120000`), `buzzer` (bool) | включает свет, запускает локальный таймер |
| `session.extend` | `session_id`, `remaining_ms`, `buzzer` | заменяет оставшееся время; только для той же сессии, иначе `wrong_session` |
| `session.stop` | `session_id`, `reason_code` | гасит свет сразу (гость нажал «Закончить» или штатное закрытие) |
| `session.resume` | как `session.start` | ответ сервера после `boot` или возврата онлайн |
| `service.start` | `duration_ms`, `reason_code` | сервисный свет на время, индикатор фиолетовый |
| `service.stop` | — | гасит сервисный свет |
| `state.reserved` | `until_ms` | индикатор синий (бронь ждёт гостя) |
| `state.pending` | `until_ms` | индикатор белый мигает (гость оплачивает) |
| `state.free` | — | индикатор зелёный тускло |
| `identify` | `duration_ms` | мигает индикатором, чтобы найти стол при монтаже |
| `config.set` | `led_brightness` (0–255), `current_on_ma`, `current_confirm_ms` (по умолчанию 10000), `grace_dim` (0–100, уровень приглушения в льготу), `grace_blink_s` (по умолчанию 15) | сохраняет в NVS |
| `ota.start` | `url`, `version`, `sha256`, `image_sig` | обновление прошивки, только при `free`, иначе `busy_ota` |
| `ping` | — | отвечает `ack` и публикует `state` |

Тихие часы пищалки решает сервер флагом `buzzer` (decisions №32).

Когда команда принимается (иначе `wrong_session`):
- `session.start`, `session.resume`, `state.free` — из любого состояния;
- `session.extend`, `session.stop` — только для своей текущей сессии;
- `service.start`, `state.pending`, `state.reserved` — только без сессии;
- команда, занимающая стол, прерывает идущее обновление: `ota_failed` с `error: aborted`.

Умолчания `config.set`: `led_brightness` 128, `current_on_ma` 50, `current_confirm_ms` 10 000, `grace_dim` 30, `grace_blink_s` 15.

Диапазоны полей тела (вне диапазона — `bad_body`):
- `session_id` — UUID в нижнем регистре; `remaining_ms` — 1…86 400 000; `warn_ms` и `grace_ms` — как в строке `session.start`;
- `duration_ms` (`service.start`, `identify`) и `until_ms` (`state.*`) — 1…86 400 000;
- `config.set`: все поля необязательны; `led_brightness` 0…255, `current_on_ma` 1…100 000, `current_confirm_ms` 1…600 000, `grace_dim` 0…100, `grace_blink_s` 1…3600;
- `ota.start`: `url` только `https://`, `sha256` — 64 шестнадцатеричных символа в нижнем регистре;
- `reason_code` — 1…32 символа `[a-z0-9_]`;
- вложенность JSON — не глубже 8.

**Почему `remaining_ms`, а не время окончания.** Часы контроллера могут расходиться с сервером. Контроллер считает остаток от момента получения команды по своему монотонному таймеру. Сервер хранит `paid_until` в UTC и при каждом `session.resume` и `session.extend` пересчитывает остаток.

## 4. Ответы, состояние, события

### `ack`
```json
{ "v": 1, "cmd_id": "0192f3c1-...", "seq": 1842, "ok": true, "error": null, "state_seq": 977 }
```
Коды ошибок: `bad_format`, `bad_sig`, `replayed_seq`, `unknown_type`, `bad_body`, `wrong_session`, `busy_ota`, `hw_fault`.
Если команду не удалось разобрать (`bad_format`), `cmd_id` и `seq` в `ack` равны `null`.

### `state` (retained)
Публикуется при каждом изменении и раз в 60 с.
```json
{
  "v": 1,
  "state_seq": 977,
  "mode": "active",
  "session_id": "0192f3c0-...",
  "remaining_ms": 2715000,
  "relay": true,
  "dim": 100,
  "led": "off",
  "buzzer": true,
  "current_ma": 412,
  "caps": ["relay", "led", "buzzer", "current"],
  "fw": "1.0.3",
  "boot": 14,
  "rssi": -61,
  "uptime_s": 86400,
  "last_seq": 1842
}
```
`mode`: `free`, `pending`, `reserved`, `active`, `ending`, `grace`, `service`, `fault`.
- `state_seq` — номер публикации `state` после загрузки, начиная с 1.
- «Изменение», после которого `state` публикуется сразу: `mode`, `session_id`, `relay`, `dim`, `led`, `buzzer`, `caps`. Остаток, ток, `rssi` и `uptime_s` сами по себе публикацию не вызывают.
- `buzzer` — флаг текущей сессии (`false`, если сессии нет). `dim` равен 0 при выключенном реле. `current_ma` равен `null`, если нет `current` в `caps`.
`led`: `off`, `green_dim`, `white_blink`, `blue`, `yellow_blink`, `red`, `red_fast`, `purple`, `identify`.
`remaining_ms` и `session_id` равны `null`, если сессии нет. В `service` поле `remaining_ms` — остаток сервисного времени.

### `event`
```json
{ "v": 1, "boot": 14, "boot_id": "9f3a61c2", "n": 3, "type": "bypass_detected", "at_uptime_ms": 123456789, "data": { "current_ma": 380 } }
```

| `type` | Когда | `data` |
|---|---|---|
| `boot` | после каждой загрузки | `fw`, `caps`, `reset_reason`: `poweron`, `sw`, `panic`, `int_wdt`, `task_wdt`, `wdt`, `deepsleep`, `brownout`, `sdio`, `unknown` |
| `bypass_detected` | ток есть, реле выключено, дольше `current_confirm_ms` | `current_ma` |
| `lamp_fault` | реле включено, тока нет дольше `current_confirm_ms` | `current_ma` |
| `relay_fault` | реле не переключается | — |
| `bad_sig`, `replayed_seq` | отвергнутая команда | `cmd_id`, `seq` |
| `offline_resume` | сессия продолжена после перезагрузки без сервера (правило 4) | `session_id`, `saved_ms`, `resumed_ms` |
| `offline_resume_denied` | вторая перезагрузка без сервера за сессию | `session_id` |
| `offline_session_finished` | сессия доиграна без связи | `session_id`, `finished_uptime_ms` |
| `ota_ok`, `ota_failed` | результат обновления | `version`, `error`: `aborted`, `rollback`, `download`, `sha256`, `image_sig`, `no_ota_key` |
| `low_memory` | мало памяти | `free_bytes` |
| `events_dropped` | буфер событий переполнился | `count` |

Каждое событие несёт `boot` (счётчик перезагрузок в NVS, для людей), `boot_id` (8 шестнадцатеричных символов, случайное значение при каждой загрузке) и `n` (номер события после этой загрузки, с 1). Сервер пишет событие в журнал один раз по `(device_id, boot_id, n)` (decisions №33, №37): после стирания NVS или замены контроллера настоящие события не теряются как дубли.
События, накопленные без связи, хранятся в кольцевом буфере на 64 события и досылаются после восстановления; в NVS пишутся только недоставленные. При переполнении вытесняется самое старое, следующим уходит `events_dropped`. События `bad_sig` и `replayed_seq` — не чаще одного каждого типа за 10 с, пропущенные считаются в `data.suppressed` следующего.

## 5. Локальная логика контроллера

```
           state.pending / state.reserved (until_ms истёк → free)
free ◀──────────────────────────────▶ pending | reserved
  │                                        │
  │ session.start / session.resume         │ session.start
  ▼                                        ▼
active ──(remaining ≤ warn_ms[0])──▶ ending ──(remaining = 0)──▶ grace ──(grace_ms)──▶ free
  ▲ │                                  │                           │
  │ └──────────── session.extend ──────┴──────── session.extend ───┘
  │
  └─ session.stop из active, ending, grace ──▶ free

free ──service.start──▶ service ──(duration_ms истёк или service.stop)──▶ free
```

Сигналы у стола (PRODUCT §7, значения по умолчанию):

| Момент | Состояние | Что делает контроллер |
|---|---|---|
| остаток пересёк `warn_ms[0]` (5 мин) | `ending` | индикатор `yellow_blink`, 2 коротких сигнала (если `buzzer`) |
| остаток пересёк `warn_ms[1]` (1 мин) | `ending` | лампа дважды мигает: выкл. 300 мс, вкл. 300 мс, выкл. 300 мс |
| `remaining = 0` | `grace` | лампа приглушается до `grace_dim` (если `dimmer`) или мигает раз в `grace_blink_s`, индикатор `red` |
| `grace_ms` истёк | `free` | свет гаснет, индикатор `green_dim` |

Сигналы срабатывают при входе в новую фазу по времени (пересечение порога, а не точное равенство). Команда, которая ставит остаток в другую фазу, вызывает сигнал этой фазы сразу и один раз; команда в пределах той же фазы сигнала не даёт. `session.start` и `session.resume` с `session_id` уже идущей сессии продолжают её: фаза, выданные сигналы и начатое мигание сохраняются, обновляются только остаток и настройки (после перезагрузки контроллера сессии в памяти нет, и сигнал текущей фазы звучит один раз). `session.extend` выше порога взводит сигналы заново. `grace_ms = 0` — льготы нет. `state.relay` — логическое состояние: мигание и приглушение его не меняют. Режим `fault` накладывается только на `free`, `pending`, `reserved`; идущая сессия доигрывается. Для частого мигания лампы рекомендуется твердотельное реле: механическое изнашивается.

Правила:
1. **Без связи идущая сессия доигрывается** до конца `remaining_ms` и льготы, затем свет гаснет. После восстановления связи контроллер отправляет `offline_session_finished` и `state`.
2. **Контроллер никогда не продлевает время сам.** Только `session.extend` с верной подписью и `seq`.
3. **Сессия в NVS:** `session_id`, остаток, параметры сигналов, `offline_resumes`. Записывается при каждой команде, в начале льготы и раз в `S` = 60 с. Состояние протокола (`seq`, сессия, буфер событий) — в отдельном разделе данных NVS на 64 КБ; ключи — в зашифрованном разделе (на классическом ESP32 это требует шифрования флеша, на C3 и S3 есть вариант на HMAC — учитывать при выборе платы). Таймеры — монотонные 64-битные (`esp_timer_get_time`), не `millis()`.
4. **После перезагрузки** (decisions №30):
   - свет выключен, `boot` увеличен, новый `boot_id`, контроллер публикует событие `boot` и ждёт `session.resume` 30 с от загрузки (Wi-Fi и TLS входят в эти 30 с); остаток в это время не идёт;
   - любая верная команда в это окно исполняется как обычно; `session.start` с другой сессией стирает сессию из NVS;
   - сервер ответил `session.resume` → продолжаем с присланным остатком, `offline_resumes` = 0;
   - сервер ответил `state.free` → `free`, сессия из NVS стирается;
   - сервер не ответил, в NVS есть сессия и `offline_resumes` = 0 → продолжаем с остатком `сохранённый − S`, записываем `offline_resumes` = 1 и событие `offline_resume`. Если остаток после вычета не больше 0 (в том числе перезагрузка в льготу) — `free`;
   - сервер не ответил, в NVS есть сессия и `offline_resumes` = 1 → `free`, событие `offline_resume_denied`;
   - в NVS сессии нет → `free`.

   Гость теряет до `S` только при пропадании питания без связи с сервером. Перезагрузками нельзя получить ни секунды сверх оплаченного.
5. **Датчик тока проверяется постоянно.** Порог `current_on_ma` и время подтверждения `current_confirm_ms` задаются `config.set`.
6. **Сигналы конца игры** исполняются локально по `warn_ms` и `grace_ms`, без ожидания команд сервера. Поэтому они срабатывают и без связи.
7. **`pending` и `reserved`** сами возвращаются в `free` по истечении `until_ms`.
8. **Watchdog** перезапускает зависшую прошивку. После перезапуска действует правило 4.

Известное поведение: если питание пропало, а сервер доступен, сервер присылает остаток по `paid_until`, и время без света не компенсируется автоматически. Компенсация — ручное действие управляющего «продление без оплаты» с причиной (инвариант 8).

## 6. Серверная сторона

- Мост `server/mqtt.mjs` — единственный, кто публикует в `cmd`.
- Перед каждой командой: проверка прав и оплаты → в одной транзакции выделение `seq` (`UPDATE devices SET last_seq = last_seq + 1 ... RETURNING`) и запись в `audit_log` с `id` и `seq` команды → публикация после коммита. Нет записи в журнале — нет команды.
- **Одна неподтверждённая команда на устройство.** Следующая команда уходит только после `ack` на предыдущую или после отказа от неё. Иначе повтор старой получил бы `replayed_seq`, и было бы неизвестно, исполнилась ли она.
- Команда без `ack` 3 с повторяется с тем же `id` и `seq`, максимум 5 раз, затем тревога «контроллер не отвечает» и отказ от команды: её больше не повторяют. Повтор не создаёт новую запись в журнале.
- Пока устройство офлайн, повторов нет и отдельной тревоги «не отвечает» нет (есть тревога офлайна). Команды `session.*`, `service.*`, `state.*`, не доставленные до офлайна, не пересылаются: после возвращения сервер шлёт актуальное состояние (ниже).
- Контроллер считается офлайн, если пришёл `status = offline` (Last Will, около 45 с) или нет `state` больше 150 с. Тревога владельцу — после 120 с непрерывного офлайна во время сессии (decisions №16).
- После `boot` или возврата онлайн сервер сам отправляет актуальное состояние стола: `session.resume` для активной сессии (остаток по `paid_until`), `service.start` с оставшимся сервисным временем, `state.pending` или `state.reserved` с оставшимся сроком, иначе `state.free`.
- Сверка `seq`: следующий `seq` = `greatest(devices.last_seq, state.last_seq) + 1`. Если сервер поднимает счётчик по `state` (база восстановлена из бэкапа), это запись в журнал `device.seq_sync`. Разрыв больше 1 000 000 — тревога без подъёма счётчика.
- Сверка: если `state.mode` расходится с сессией в базе дольше 10 с, пишется событие и уходит тревога.
- Событие контроллера пишется в журнал один раз по `(device_id, boot_id, n)`.

## 7. Привязка контроллера (provisioning)

1. Новый контроллер стартует точкой доступа `Billiardum-XXXX` с портальной страницей.
2. На корпусе наклейка с QR: `device_id` и одноразовый код привязки — не короче 8 символов (он же пароль точки доступа).
3. Владелец или монтажник в программе клуба: «Добавить контроллер» → скан QR → выбор стола → ввод Wi-Fi клуба. С этого момента у привязки есть окно 30 минут.
4. Контроллер подключается к Wi-Fi и вызывает `POST /api/devices/claim` с `device_id` и кодом привязки. Пока окна привязки нет или код отклонён с `forbidden`, повторяет запрос через 5, 10, 20 с, затем раз в 30 с (+ до 20 % случайно); на `rate_limited` ждёт 60 с; на `bad_request` не повторяет до перезапуска. Без сети код не тратится. Код привязки — 8…63 символа `[A-Za-z0-9-]` (он же пароль точки доступа WPA2); заводская наклейка — QR `BLD1:{device_id}:{claim_code}`, консоль принимает `factory <device_id> <claim_code>` и `factory BLD1:…` (M5.1, №159).
5. Сервер привязывает устройство к клубу и столу, создаёт клиента и роль в Dynamic Security, выдаёт пароль MQTT и `device_key`. Код привязки сгорает. Без начатой владельцем привязки код не принимается.
6. Контроллер сохраняет ключи в зашифрованном разделе NVS, обнуляет `seq`, `id`, `ack` и подключается к брокеру.

## 8. Обновление прошивки

- Только по явному «да» Андрея и только на столах в состоянии `free`.
- Сначала один стол, затем остальные по одному.
- `image_sig` — base64 DER-подписи ECDSA P-256 над SHA-256 файла `.bin`; `sha256` — от того же файла. Ключ проверки зашит в прошивку.
- Контроллер проверяет `sha256` и подпись образа `image_sig`. Новая прошивка помечается рабочей только после успешного подключения к брокеру, иначе откат на предыдущую.

## 9. Симулятор (`tools/device-sim/`)

- Говорит с сервером по этому же протоколу, поднимает N виртуальных столов.
- Повторяет конечный автомат прошивки один в один и проходит `docs/protocol-vectors.json`.
- Печатает состояние: свет, приглушение, индикатор, пищалка, остаток.
- Умеет имитировать: обрыв связи, перезагрузку, свет в обход (ток при выключенном реле), неисправную лампу, медленный `ack`, повтор старой команды.
- На симуляторе работают tester, pentester и backend. Сценарии в `docs/ROADMAP.md`.
