# Протокол контроллера стола, черновик v0

Статус: черновик. Утверждают оркестратор, firmware и backend на этапе M0, после этого версия становится `v1`.
Любое изменение после утверждения — только через оркестратора и с согласия обеих сторон. Несовместимое изменение повышает версию в топике.

---

## 1. Железо одного стола

| Узел | Назначение | Обязателен |
|---|---|---|
| ESP32 (Wi-Fi) | логика, связь, таймер | да |
| Реле или твердотельное реле на линию лампы | свет | да |
| Индикатор (RGB-светодиод, например WS2812) | состояние стола гостю | да |
| Пищалка | сигнал конца игры | да |
| Датчик тока на линии лампы (бесконтактный трансформатор тока или модуль на эффекте Холла) | свет в обход системы, неисправность лампы | да |
| Блок питания 220 → 5 В, корпус, предохранитель | питание и безопасность | да |
| Выход ШИМ или 0–10 В на диммер | приглушение в льготу | если лампа диммируемая |

Два пути для пилота, решает Андрей:
- **A. Своя плата.** Полный контроль, датчик тока и индикатор сразу. Дольше до первого стола.
- **B. Готовое Wi-Fi-реле на ESP32 с нашей прошивкой.** Быстрее к пилоту. Индикатор, пищалку и датчик тока придётся добавить или отложить.

Прошивка пишется с прослойкой драйверов (`relay`, `led`, `buzzer`, `current`, `dimmer`), чтобы смена платы не меняла логику и протокол.

Монтаж в линию 220 В делает только электрик.

## 2. Связь

- MQTT 3.1.1 по TLS (порт 8883), брокер Mosquitto на сервере платформы.
- Сертификат сервера закреплён в прошивке (CA pinning).
- У каждого контроллера свой логин (`device_id`) и пароль. ACL Mosquitto разрешает устройству только его собственные топики.
- Сервер подключается отдельной учётной записью с доступом ко всем топикам.
- `keepalive` 30 с. Last Will: `status` = `offline`, retained.

### Топики

Префикс: `bl/v1/{club_id}/{device_id}/`

| Топик | Направление | QoS | Retained | Содержимое |
|---|---|---|---|---|
| `cmd` | сервер → контроллер | 1 | нет | команды |
| `ack` | контроллер → сервер | 1 | нет | подтверждение команды |
| `state` | контроллер → сервер | 1 | да | текущее состояние |
| `event` | контроллер → сервер | 1 | нет | события (тревоги, перезагрузка) |
| `status` | контроллер → сервер | 1 | да | `online` или `offline` (Last Will) |

## 3. Команды (`cmd`)

Общий вид:

```json
{
  "v": 1,
  "id": "0192f3c1-6d1a-7c3e-9b2a-1f0e5d4c3b2a",
  "seq": 1842,
  "type": "session.start",
  "issued_at": 1792598400,
  "body": { },
  "sig": "base64(HMAC-SHA256(device_key, canonical_json_without_sig))"
}
```

- `seq` строго растёт для каждого устройства. Контроллер хранит последний принятый `seq` в NVS и отвергает команды с `seq` не больше сохранённого (защита от повтора).
- `sig` проверяется контроллером. Ключ `device_key` выдаётся при привязке и не совпадает с паролем MQTT. Даже при компрометации брокера чужую команду не подписать.
- Канонический JSON: ключи по алфавиту, без пробелов, без поля `sig`.

### Типы команд

| `type` | `body` | Что делает контроллер |
|---|---|---|
| `session.start` | `session_id`, `remaining_ms`, `warn_ms` (массив, по умолчанию `[300000, 60000]`), `grace_ms` (120000) | включает свет, запускает локальный таймер |
| `session.extend` | `session_id`, `remaining_ms` | заменяет оставшееся время (только для той же сессии) |
| `session.stop` | `session_id`, `reason` | гасит свет сразу (гость нажал «Закончить» или штатное закрытие) |
| `session.resume` | как `session.start` | ответ сервера на `sync` после перезагрузки или потери связи |
| `service.start` | `duration_ms`, `reason_code` | сервисный свет на время, индикатор фиолетовый |
| `service.stop` | — | гасит сервисный свет |
| `state.reserved` | `until_ms` | индикатор синий (бронь ждёт гостя) |
| `state.pending` | `until_ms` | индикатор белый мигает (гость оплачивает) |
| `state.free` | — | индикатор зелёный тускло |
| `identify` | `duration_ms` | мигает индикатором, чтобы найти стол при монтаже |
| `config.set` | сигналы, яркость индикатора, тихие часы пищалки, порог тока | сохраняет в NVS |
| `ota.start` | `url`, `version`, `sha256`, `sig` | обновление прошивки, только при `free` |
| `ping` | — | отвечает `ack` с текущим состоянием |

**Почему `remaining_ms`, а не время окончания.** Часы контроллера могут расходиться с сервером. Контроллер считает остаток от момента получения команды по своему монотонному таймеру. Сервер хранит `paid_until` в UTC и при каждом `sync` пересчитывает остаток.

## 4. Ответы и состояние

### `ack`
```json
{ "v": 1, "cmd_id": "0192f3c1-...", "ok": true, "error": null, "state_seq": 977 }
```
Коды ошибок: `bad_sig`, `replayed_seq`, `wrong_session`, `busy_ota`, `unknown_type`, `hw_fault`.

### `state` (retained)
Публикуется при каждом изменении и раз в 60 с.
```json
{
  "v": 1,
  "state_seq": 977,
  "mode": "active",
  "session_id": "0192f3c0-...",
  "remaining_ms": 2715000,
  "relay": true,
  "dim": 100,
  "led": "off",
  "current_ma": 412,
  "fw": "1.0.3",
  "rssi": -61,
  "uptime_s": 86400,
  "last_seq": 1842
}
```
`mode`: `free`, `pending`, `reserved`, `active`, `ending`, `grace`, `service`, `fault`.

### `event`
```json
{ "v": 1, "type": "bypass_detected", "at_uptime_ms": 123456789, "data": { "current_ma": 380 } }
```
Типы: `boot`, `bypass_detected` (ток есть, реле выключено, дольше 10 с), `lamp_fault` (реле включено, тока нет дольше 10 с), `relay_fault`, `offline_session_finished` (сессия доиграна без связи), `ota_ok`, `ota_failed`, `low_memory`.
События, накопленные без связи, хранятся в кольцевом буфере в NVS и досылаются после восстановления.

## 5. Локальная логика контроллера

```
free ──session.start──▶ active ──(remaining ≤ 5 мин)──▶ ending ──(remaining = 0)──▶ grace ──(grace_ms)──▶ free
  ▲                        │  ▲                            │                            │
  │                        │  └──────session.extend────────┴────────session.extend───────┘
  │                        └──session.stop──▶ free
  └──service.stop── service ◀──service.start── free
```

Правила:
1. **Без связи идущая сессия доигрывается** до `remaining_ms` плюс льгота, затем свет гаснет. После восстановления связи контроллер отправляет `offline_session_finished` и `state`.
2. **Контроллер никогда не продлевает время сам.** Только `session.extend` с верной подписью.
3. **Оставшееся время сохраняется в NVS** при каждом изменении и раз в 60 с.
4. **После перезагрузки** свет выключен, контроллер публикует `boot` и ждёт `session.resume` 30 с.
   - Сервер ответил: продолжаем с присланным остатком.
   - Сервер не ответил, в NVS есть активная сессия: продолжаем с сохранённым остатком. Гость теряет не больше 60 с и не получает лишнего: пока питания не было, лампа не горела. Это решение предварительное, утверждает Андрей.
   - В NVS сессии нет: остаёмся в `free`.
5. **Датчик тока проверяется постоянно.** Порог и время подтверждения задаются `config.set`.
6. **Сигналы конца игры** исполняются локально по `warn_ms` и `grace_ms`, без ожидания команд сервера. Поэтому они срабатывают и без связи.
7. **Watchdog** перезапускает зависшую прошивку. После перезапуска действует правило 4.

## 6. Серверная сторона

- Мост `server/mqtt.mjs` — единственный, кто публикует в `cmd`.
- Перед каждой командой проверяет права и оплату, пишет запись в `audit_log`, затем публикует.
- Команда без `ack` 3 с повторяется с тем же `id` и `seq` (идемпотентно), максимум 5 раз, затем тревога «контроллер не отвечает».
- Контроллер считается офлайн, если нет `state` больше 150 с или пришёл `status = offline`.
- После `boot` или возврата онлайн сервер сам отправляет `session.resume` для активной сессии или `state.free`.
- Сверка: если `state.mode` расходится с сессией в базе дольше 10 с, пишется событие и уходит тревога.

## 7. Привязка контроллера (provisioning)

1. Новый контроллер стартует точкой доступа `Billiardum-XXXX` с портальной страницей.
2. На корпусе наклейка с QR: `device_id` и одноразовый код привязки.
3. Владелец или монтажник в программе клуба: «Добавить контроллер» → скан QR → выбор стола → ввод Wi-Fi клуба.
4. Контроллер подключается к Wi-Fi и вызывает `POST /api/devices/claim` с `device_id` и кодом привязки.
5. Сервер привязывает устройство к клубу и столу, выдаёт пароль MQTT и `device_key`. Код привязки сгорает.
6. Контроллер сохраняет ключи в зашифрованном разделе NVS и подключается к брокеру.

---

## 8. Обновление прошивки

- Только по явному «да» Андрея и только на столах в состоянии `free`.
- Сначала один стол, затем остальные по одному.
- Контроллер проверяет `sha256` и подпись образа. Новая прошивка помечается рабочей только после успешного подключения к брокеру, иначе откат на предыдущую.

## 9. Симулятор (`tools/device-sim/`)

- Говорит с сервером по этому же протоколу, поднимает N виртуальных столов.
- Печатает состояние: свет, приглушение, индикатор, пищалка, остаток.
- Умеет имитировать: обрыв связи, перезагрузку, свет в обход (ток при выключенном реле), неисправную лампу, медленный `ack`, повтор старой команды.
- На симуляторе работают tester, pentester и backend. Сценарии в `docs/ROADMAP.md`.
