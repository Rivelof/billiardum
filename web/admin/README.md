# @billiardum/web-admin — программа клуба

Адрес `/club/` (Vite + Preact, JS ESM, без UI-библиотек — decisions №51). Экраны M1 по `docs/contracts/m1.md` §10, M2 (касса, бар, смены, склад, меню, ККТ) — по `docs/contracts/m2.md` и коду backend-pos и backend-kkt. Владелец и управляющий — сначала телефон (разделы снизу), ресепшн — планшет горизонтально (разделы слева, очередь и зал рядом, крупные плитки, всё с клавиатуры и пальцем).

## Запуск

```sh
npm run dev:mock -w web/admin     # заглушка API: http://127.0.0.1:5174/club/
npm run dev -w web/admin          # настоящий API: прокси /api → BL_API_URL (по умолчанию http://127.0.0.1:3000)
npm run build -w web/admin        # dist/ для Caddy (/club/* → web/admin/dist)
npm test -w web/admin             # node --test: сдача, сутки клуба, журнал, тревоги, зал, касса (скидка, лимит, тело продажи), смена (расхождение, отчёт), склад (ревизия), CSV, заглушка
```

## Как устроено

- `src/lib/` — логика без JSX: `pos.js` (скидка как у сервера — целый процент, «половина вверх» до копейки, только на бар; лимит; тело `POST /api/pos/sales`; вид продажи и кассы ККТ; чек словами), `shift.js` (ожидаемые наличные, расхождение, отчёт), `stock.js` (количество до тысячных, ревизия в деньгах), `csv.js` (CSV меню и ошибки сервера словами), `cash.js` (ввод суммы, сдача, быстрые суммы, клавиатура — целые копейки), `zone.js` (сутки клуба по его поясу для фильтра журнала), `audit.js` (действия журнала словами, группы фильтра), `alarms.js`, `sound.js`, `hall.js`, `auth.js` (роли), `api.js`.
- План зала — `src/components/HallPlan.jsx` на `@billiardum/shared/hall`: столы в настоящих пропорциях, свободные тёмные, занятые освещены, у каждого стола подпись словом и метка для диктора.
- Живые обновления — SSE `GET /api/stream?club=…` (`hall`, `reception_request`, `alarm`, `session`), при разрыве — переподключение и перечитывание, запасной опрос.
- Вход — cookie `bl_session` (§14); клуб для маршрутов без `{club}` — заголовок `X-Club-Id` во всех запросах.
- Терминал: `POST /api/staff/terminal` → `terminal_token` в `localStorage`; `GET /api/staff/terminal` и `POST /api/staff/pin` получают его как `Authorization: Bearer`. После PIN сервер сам ставит cookie сотрудника.
- «Принять оплату»: сервер отвечает `session_id: null` (сессия создаётся асинхронно) — окно ждёт стол в зале по SSE `hall` и опросу и пишет «Свет на столе N включён».
- Журнал: фильтр `action` списком через запятую (§14); если сервер его ещё не принимает (`400`), программа переходит на старый вид (`session.`) или фильтрует на клиенте.

- Корзина POS из `@billiardum/shared/bar` (меню, модификаторы, строки), живёт в `sessionStorage` до оплаты. Ключ идемпотентности продажи — на одно окно оплаты.
- QR для СБП — `uqr` (MIT), SVG без атрибутов `style`, всегда тёмные модули на светлом поле.

## Заглушка API (`VITE_MOCK=1` или `--mode mock`)

`src/mock/` — поддельный сервер по контракту, новая заявка приходит раз в минуту (слышно звук). Сценарии `?mock=`: `reception` (по умолчанию), `owner`, `manager`, `anon`, `empty`, `broken` (цепочка нарушена), `terminal` (устройство — терминал; PIN `1234`); M2 (`src/mock/m2.js`, вид ответов — как у backend-pos и backend-kkt): `pos` (смена открыта), `noshift`, `kktoff` (касса ККТ не на связи, чек «исход неизвестен»; `kktoff-owner` — то же под владельцем), `bar` (бармен). PIN управляющего для скидки — `1234`; СБП «оплачивается» через 9 секунд, чек ККТ пробивается через 2,5 секунды, новый заказ со стола — раз в 75 секунд. Клуб: `/club/c/0b6b8c1e-5a7d-4f0e-9c3a-2d1e4f5a6b7c/…`. Вход разработки: номер на `…01` — владелец, `…02` — управляющий, `…05` — бар, остальные — ресепшн.

## M3: живой API (волна B, №118, №120)

- План зала (Ресепшн, Сейчас): ближайшая бронь — `next_booking {id, starts_at, ends_at, source, status}` у стола в ответе зала; янтарная рамка и «Бронь 21:00» — только если бронь в ближайшие 12 часов (`BOOKED_HORIZON_MS` в `shared/hall.mjs`). Депозит — `session.deposit_kopecks`.
- Отмена брони: кнопка — по `can_cancel` из списка броней (правило №115 решает сервер). События клуба `booking` несут `type`.
- Возврат пакета (№118, управляющий и владелец) — раздел «Возврат пакета» на экране «Пакеты»: поиск партий по точному телефону `GET /api/clubs/{club}/package-lots?phone=+7…` (ввод `8…` переводим в `+7…` на клиенте), вернуть можно только нетронутую партию целиком и с причиной. Из приложения — `POST /api/packages/lots/{id}/refund {reason}`, с кассы — `POST /api/pos/sales/{sale_id}/refund {reason, packages: [idx]}`, оба с `Idempotency-Key` на одно окно; `409 package_used`, `already_refunded`.
- Тревога `payment_not_found_at_provider`: «Платёж не найден в ЮKassa — отменён» (`data.action: canceled`) или «Платёж не найден в ЮKassa» — у нас проведён (`kept`, критично).
- Заглушка: у гостя `+79123456789` три пакета — нетронутый из приложения, начатый и с кассы.

## M3: исправления по tester (№122, №125, Д2)

- План зала: стол, предложенный из очереди, — `hold {source: 'waitlist', until, offer_id}`: подпись «Из очереди до HH:MM», в окне стола — «Предложен из очереди до HH:MM» и «Снять удержание» (ресепшн и выше, причина) → `POST /api/waitlist/offers/{offer_id}/release`; `offer_expired` — предложение уже закончилось. Заглушка: `?mock=waitlist`.
- Отчёт смены: ручные действия и действия персонала — общим списком (`kind: manual | staff`); денежные записи той же операции сервер склеивает с ней (`linked`) — мелко «вместе с: …». Свёрнутыми строками — «Действия гостей» (`manual_actions.guests`, например поздняя отмена брони гостем с возвратом) и «Автоматические действия системы» (`manual_actions.automatic`).
- Тревоги: у `settlement_receipt_failed` с `data.action_id: 'retry'` — кнопка «Повторить» (управляющий и владелец, причина, один `Idempotency-Key` на окно) → `POST /api/receipts/{id}/retry`. Кнопка появляется только для адреса вида `/api/receipts/{uuid}/retry`.
- Тревоги M4 (№147): `tournament_match_overdue` — «Матч турнира затянулся», время «свет погаснет в 21:30» по поясу клуба из `data.light_until`; `manual_action` с `data.action` `manual.tournament_score` (было → стало, причина), `plus.match_resolve` (решение по партии, причина) и `tournament_cancel` — свои тексты, сотрудник — в журнале. Переход из тревоги: «Открыть турнир» → `/club/c/{club}/tournaments/{tournament_id}` (только UUID), «Открыть споры по партиям» → `/club/c/{club}/disputes`. В журнале и отчёте смены `manual.tournament_score`, `manual.tournament_cancel` и `plus.match_resolve` — ручные строки.

## M4: турнир после старта (№147–149)

- Экран турнира: «Продлить турнир» (только `running`) → `POST …/tournaments/{id}/extend {ends_at?, match_minutes?, reason}`; уходят только изменённые поля, причина обязательна. Подсказка «не дальше 12 часов от текущего момента»; на 409 `limit_exceeded` — «Так далеко продлить нельзя: не позже HH:MM» по `extend_limit_until` и кнопка «Поставить HH:MM». «Изменить» → PATCH: до старта — название, призы, места, время; после старта — только название и призы, вместо полей времени — текущее окно и «Продлить турнир» (время в PATCH не отправляется; на 409 `tournament_started` та же кнопка).
- Отмена до старта — `{reason}`, возврат всем (№138). После старта по умолчанию `{reason, refund: 'none'}` и плашка «Взносы не возвращаются: время стола уже занято»; переключатель «Вернуть взносы всем» открывает выбор «Поломка оборудования» / «Авария в клубе (свет, помещение)» (`reason_code` `equipment` | `venue`) и обязательный комментарий → `{reason, refund: 'all', reason_code}`. Ответ `{refunded}` — детали турнира перечитываются.
- Участники: оплата словом («оплачен», «возврат оформляется», «взнос возвращён», «ждём оплату»); после старта у оплатившего — «Вернуть взнос» → `POST …/entries/{entry_id}/refund {reason_code: health|equipment|venue, comment}`, подпись «Личные причины не основание для возврата». Коды: `not_paid`, `already_refunded`, `bad_status`, `reason_required`.
- Тревоги `manual_action`: `manual.tournament_extend` — «Турнир продлён» (было → стало, причина, «Продлил: имя»), `manual.tournament_refund` — «Возврат взноса 500 ₽» (ник, если сервер пришлёт `data.nick`; основание, комментарий, кто), `tournament_cancel` — одна тревога об отмене: без возврата («Турнир отменён после старта… взносы не возвращаются») или с возвратом (сколько игроков и сумма, основание). У `manual.tournament_score` и `plus.match_resolve` — имя из `data.staff_name` вместо «кто — в журнале» (старые тревоги без имени — прежний текст). `tournament_match_overdue` — «— предел матча» или «— предел окна турнира» по `limit_by`. Все турнирные — с переходом «Открыть турнир».
- Отчёт смены: строки `manual.tournament_score`, `plus.match_resolve`, `manual.tournament_extend` (окно по времени клуба) показывают «было → стало», `manual.tournament_refund` — кому и основание; по `data.tournament_id` (UUID) — ссылка «Открыть турнир» (`manualDetail` в `lib/shift.js`).
- Матч `canceled` (после отмены идущего турнира): в сетке и на ТВ — «Отменён» словом, без стола; исправить счёт такого матча нельзя (не кнопка), в «Сейчас играют» не попадает.
- Сетка организатора (Д8, WCAG 2.5.3): у кнопки матча нет `aria-label` — её имя совпадает с видимым текстом (посев, ник, счёт, статус), а действие «Исправить счёт матча» — в `aria-describedby` (скрытый абзац один на сетку). `.abracket` — `position: relative`, скрытое не выходит за край.
- Уведомление `tournament.confirm_reminder` приходит в мессенджер со ссылкой `/club/tournaments/{id}`; своей таблицы уведомлений в программе нет — короткий адрес уже ведёт в турнир первого клуба организатора.
- Заглушка: «Вечерний пул» идёт со взносом 500 ₽ (`?mock=manager`): продление (предел +12 ч, 409 с `extend_limit_until`), возврат одному, отмена с выбором возврата, PATCH времени — 409 `tournament_started`.

## M2: живой API (волна B, decisions №86–98)

Все экраны M2 работают с сервером; заглушка повторяет его правила. Что важно знать:

- Смена: ресепшну `shifts/current` отдаёт смену вслепую — закрытие «введите, сколько насчитали», ожидаемое и расхождение приходят в ответе закрытия. Управляющему и владельцу — `expected_cash_kopecks`, `cash_sales_kopecks`, `cash_refunds_kopecks` до закрытия.
- Скидка выше лимита у ресепшена: `GET /api/clubs/{club}/staff/approvers`, `POST /api/pos/discount-approvals {user_id, pin, reason_code, reason_text, percent | amount_kopecks, subtotal_kopecks}` → `{approval_id, expires_at, subtotal_kopecks, max_discount_kopecks}` (5 минут, одноразовое, на сумму бара в чеке, №100), в продаже `discount.approval_id` с той же скидкой. 401 — «Неверный PIN», 403 — «не может подтвердить», 429 — «PIN заблокирован»; продажа с корзиной крупнее одобренной, большей скидкой или истёкшим подтверждением — 403: «Корзина изменилась — подтвердите скидку заново» и кнопка, которая открывает скидку с теми же значениями.
- СБП: закрыть окно с QR — `POST /api/pos/sales/{id}/cancel {reason}`; 409 `already_paid` — гость успел оплатить, окно показывает оплату.
- Продажа: `receipt_status`, `receipt_fd`, `receipt_fp` — «Чек пробит, ФД № …».
- Позиция заказа и продажи: `product_name` — имя товара, `name` — имя для чека с модификаторами («Чай чёрный, С сахаром»), `modifiers` отдельно; экраны берут `product_name`, без него отрезают хвост от `name` (`itemView` в `shared/bar.mjs`).
- SSE клуба: `stop_list {product_id, stop_list, active}` — касса и экран бара перечитывают меню. Бармену (роль `bar`) сервер шлёт только `bar` и `stop_list`.
- Роль `bar`: экран бара, статусы заказов (без отмены), стоп-лист. Касса, счета столов, смены — 403. Маршрута «добавить сотрудника» в API пока нет: бармена заводят в базе.
- Отчёт смены: `play.by_resource` — загрузка по столам, `resource_number` в ручных действиях; список смен — `revenue_total_kopecks`.
- Ресепшн без открытой смены: заявку стола не принять (409 `shift_closed`), экран ресепшена заранее показывает «Смена не открыта».

## M5.1: подключение клуба без выезда (docs/contracts/m5-1.md, №152–160)
