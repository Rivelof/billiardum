# Прошивка контроллера стола (`firmware/`)

ESP32, PlatformIO, Arduino-ESP32 2.0.17 (ESP-IDF 4.4). Говорит с сервером по `docs/protocol.md` v1: MQTT по TLS, подписанные команды, локальный таймер игры и сигналы конца игры.

Проверка на 23.10.2026 (M5.1):
- логика (`lib/logic`) проверена нативно: CMake + g++ и clang, с AddressSanitizer и UBSan;
- `pio test -e native` в среде агентов не запускается: PlatformIO ставится, но реестр платформ (`native`, `espressif32`) из среды закрыт (`HTTPClientError`). Тот же набор тестов собирается CMake;
- код для ESP32 (`src/`, `lib/drivers`, `lib/platform`) **не компилировался** по той же причине. Синтаксис сверен с заглушками заголовков Arduino-ESP32 2.0.17. Первая сборка — `pio run -e esp32dev` у Андрея или в CI.

## Что умеет

- Логика — чистый C++17 без Arduino, исключений и RTTI (`lib/logic`):
  - строгий JSON и каноническая строка §3.1;
  - HMAC-SHA256, сравнение подписи за постоянное время;
  - повторы §3.2, тело и диапазоны §3.3;
  - автомат §5, сигналы конца игры, правило 4;
  - кольцевой буфер событий на 64, ограничение частоты `bad_sig` и `replayed_seq`;
  - `state` и `ack` по §4.
- Тот же автомат, что в симуляторе `tools/device-sim/lib/machine.mjs`, построчно. Общие сценарии `tools/device-sim/scenarios/*.json` прогоняются и здесь, и в симуляторе. Расхождение — дефект.
- После старта реле выключено. Время продлевает только `session.extend` с верной подписью и `seq`. Без связи сессия доигрывается до конца остатка и льготы, затем свет гаснет. Режима «свет всегда включён» нет.

## Железо

| Узел | `caps` | Пин по умолчанию (путь A) | Чем задаётся |
|---|---|---|---|
| Реле или твердотельное реле лампы | `relay` | GPIO 26, активный уровень высокий | `BL_PIN_RELAY`, `BL_RELAY_ACTIVE_HIGH` |
| Индикатор WS2812, один светодиод | `led` | GPIO 27 | `BL_PIN_LED` |
| Пищалка активная | `buzzer` | GPIO 25 | `BL_PIN_BUZZER` |
| Трансформатор тока на линии лампы | `current` | GPIO 34 (АЦП1) | `BL_PIN_CURRENT`, `BL_CT_MA_PER_MV` |
| Диммер: ШИМ или модуль 0–10 В | `dimmer` | нет | `BL_PIN_DIMMER` |

Пины задаются в `build_flags` в `platformio.ini`. Пин `-1` — узла нет, его нет и в `caps`, логика от платы не зависит.

**Путь A — своя плата.** Все узлы сразу. Требования к схеме:
- подтяжка затвора или входа реле к «выключено»: от сброса до `setup()` выводы ESP32 висят в воздухе;
- твердотельное реле для мигания лампой: механическое реле изнашивается (§5);
- трансформатор тока, например SCT-013-030, на нагрузочном резисторе со смещением Vcc/2 на вход АЦП1. `BL_CT_MA_PER_MV` калибруется на стенде;
- блок питания 220 → 5 В, предохранитель, корпус;
- флеш не меньше 4 МБ: два раздела приложения для отката.

**Путь B — готовое Wi-Fi-реле на ESP32 с нашей прошивкой.** Задаются только `BL_PIN_RELAY` и, если есть, индикатор, остальное `-1`. Например, `caps: ["relay"]` — без пищалки и датчика тока. Сервер показывает владельцу, что защиты от света в обход на этом столе нет. Сценарий `18-caps-relay-only.json` проверяет такой контроллер.

Разделы флеша — `partitions.csv`:

| Раздел | Размер | Назначение |
|---|---|---|
| `app0`, `app1` | по 1,75 МБ | две прошивки для OTA с откатом |
| `bl_state` | 64 КБ | состояние протокола: `seq`, `id` и `ack` одним блоком, сессия, `config.set`, буфер событий, `boot` |
| `bl_keys` | 24 КБ | ключи и настройки привязки (шифруется ключами `nvs_keys`) |
| `nvs_keys` | 4 КБ | ключи шифрования NVS |

## Сборка

```sh
cd firmware
cp /путь/к/certs.local.h src/certs.local.h   # CA брокера, CA HTTPS и ключ OTA (ниже)
pio run -e esp32dev
```

`src/certs.local.h` не хранится в git, у прода и стенда разработки он разный:

```cpp
static const char kMqttCaPem[] = "-----BEGIN CERTIFICATE-----\n...";   // CA брокера (для стенда: deploy/dev/certs/ca.crt)
static const char kApiCaPem[] = "-----BEGIN CERTIFICATE-----\n...";    // CA HTTPS API и сервера образов
static const char kOtaPubKeyPem[] = "-----BEGIN PUBLIC KEY-----\n..."; // ECDSA P-256 для image_sig
```

Без файла прошивка собирается, это нужно для проверки сборки в CI. Но она ни к чему не подключится: TLS без закреплённого CA не устанавливается, свет без команд сервера не включается.

Адрес API для привязки задаёт `BL_API_URL`, версию — `BL_FW_VERSION`.

## Тесты

Без PlatformIO, в этой среде и в CI:

```sh
cmake -S firmware/test/native -B build/fw-native && cmake --build build/fw-native -j
ctest --test-dir build/fw-native --no-tests=error --output-on-failure
# с санитайзерами: -DBL_SANITIZE=ON
```

С PlatformIO, на машине Андрея: `pio test -e native`. Тот же набор `test/native/test_logic`, doctest 2.4.12. В репозитории есть копия doctest с лицензией: `test/vendor/doctest/`.

Что проверяется:
- все 38 векторов `docs/protocol-vectors.json`: результат, каноническая строка, подпись и проход вектора через автомат до `ack`;
- строгий JSON: повторяющиеся ключи, обратная косая черта, `-0`, `1.0`, `9e5`, ведущие нули, 2048 байт, вложенность 8, вложенный `sig`;
- SHA-256 и HMAC по эталонам FIPS 180 и RFC 4231, base64 и `sig`;
- таблица §3.2 и порядок «исполнить → блок в NVS → `ack`»;
- диапазоны §3.3, включая `reason_code` 1…32 символа `[a-z0-9_]`;
- все общие сценарии `tools/device-sim/scenarios/*.json`;
- привязка: векторы `tools/device-sim/test/claim-vectors.json` — разбор `factory` и `BLD1`, задержки повтора `claim`. Их же проходит симулятор;
- правило 4: окно ожидания, `сохранённый − S`, вторая перезагрузка, цикл перезагрузок без сервера не даёт ни секунды сверх оплаченного;
- буфер событий на 64, `events_dropped`, запись в NVS только без связи, ограничение частоты событий.

## Прошивка контроллера

- На стенде: `pio run -e esp32dev -t upload`, лог — `pio device monitor` (строки JSON).
- В клубе — только OTA, по явному «да» Андрея. Сначала один свободный стол, затем остальные по одному. Это делает devops.

На производстве в контроллер записываются данные с наклейки. Их выдаёт `scripts/provision-factory.mjs` (решение №159): наклейку с QR `BLD1:{device_id}:{claim_code}` и строку консоли `factory …`. Служебная консоль USB, 115200, доступна только при физическом доступе к плате:
- `factory <device_id> <claim_code>` или `factory BLD1:<device_id>:<claim_code>` (строка QR, можно сканером USB) — один раз:
  - `device_id` — UUID, хранится строчными;
  - `claim_code` — 8…63 символа `[A-Za-z0-9-]`, регистр значим. Он же пароль точки доступа, а пароль WPA2 — не длиннее 63;
  - ответ в лог: `factory_saved`, `factory_already_set`, `bad_factory_args`;
- `wifi <ssid> <пароль>` — сменить Wi-Fi клуба без перепривязки;
- `unclaim` — сбросить привязку;
- `reboot`.

## Привязка (§7, PRODUCT §16)

1. Непривязанный контроллер поднимает точку доступа `Billiardum-XXXX`. Пароль — код привязки с наклейки.
2. Владелец в программе клуба нажимает «Добавить контроллер», сканирует QR и выбирает стол. Открывается окно привязки на 30 минут.
3. Монтажник подключается к точке доступа. Портальная страница открывается сама; на ней — Wi-Fi клуба и пароль.
4. Контроллер подключается к Wi-Fi и вызывает `POST {BL_API_URL}/api/devices/claim` с `{device_id, claim_code}`. Это HTTPS с закреплённым `kApiCaPem`. На время запроса задача снимается со сторожа: запрос может идти дольше срока сторожа (5 с в Arduino-ESP32 2.x).
   - Если сервер не принял код, контроллер повторяет запрос сам (`lib/logic/src/bl_claim.*`, как симулятор): через 5 с, 10 с, 20 с, затем раз в 30 с, плюс случайные до 20 %. Так монтажник может ввести Wi-Fi раньше, чем владелец начнёт привязку.
   - `rate_limited` — пауза 60 с: за NAT клуба лимит по IP общий.
   - `bad_request` — без повтора. На портале — «сообщите в поддержку», повтор — кнопкой «Подключить».
   - Пока Wi-Fi нет, код не тратится.
5. Ответ `{mqtt_username, mqtt_password, device_key, mqtt_url, club_id}` сохраняется в `bl_keys`. `seq`, `id`, `ack` и сессия в `bl_state` обнуляются. Контроллер перезагружается и подключается к брокеру.

## Безопасность

- **Монтаж в линию 220 В делает только электрик.**
- После старта реле выключено: драйвер реле запускается первым в `setup()`, затем правило 4.
- Режима «свет всегда включён» нет. Без команды сервера свет не включается. Исключение — правило 4: «сохранённый − 60 с», один раз за сессию.
- Связь: MQTT 3.1.1 по TLS с закреплённым CA, QoS 1, `clean session`, Last Will `offline`. Логин MQTT и `device_key` — разные секреты.
- Подпись сравнивается за постоянное время. Команда, её подпись и ключи не пишутся в лог.
- Ключи хранятся в разделе `bl_keys`. Ограничение готовой сборки Arduino-ESP32 2.x: в ней нет `CONFIG_NVS_ENCRYPTION`, поэтому раздел не шифруется. При старте в лог уходит `nvs_keys_unencrypted`. Шифрование требует:
  - Arduino как компонента ESP-IDF со своим `sdkconfig`;
  - шифрования флеша. Оно необратимо прожигает eFuse, решение — за Андреем вместе с выбором платы. На ESP32-C3 и S3 есть вариант на HMAC (§5 правило 3).
- OTA:
  - только в `free`;
  - SHA-256 и подпись `image_sig` (ECDSA P-256, ключ закреплён) проверяются по образу, уже записанному во флеш;
  - команда, занимающая стол, прерывает загрузку: событие `ota_failed`, `error: aborted`;
  - перезагрузка в новую прошивку — только на свободном столе;
  - новая прошивка становится рабочей после подписки на `cmd` у брокера. Если брокера нет 10 минут или прошивка падает раньше — откат. Старая прошивка сообщает `ota_failed` с `error: rollback`.
- Watchdog задачи `loop()`. Сбой — перезагрузка по правилу 4, `reset_reason` в событии `boot`.
